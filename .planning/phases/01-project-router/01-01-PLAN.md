**## Overview** — One paragraph: plain-text checkbox notation, two-tier state (project-level progress.txt, milestone-level milestone-status.txt).

**## Status Notation** — The four canonical markers used everywhere:
- `[x]` = complete
- `[~]` = in progress
- `[ ]` = pending
- `[-]` = skipped / not applicable

State that these four markers are the ONLY status markers. No other bracket notation (e.g., `[in-progress]`) is permitted. Reference DESIGN.md DD-3 and the TEXT_vs_YAML_REPORT.md consistency risk.

**## Bootstrap Template** — The exact progress.txt content created on first run. Use the format from DESIGN.md indicative example and RESEARCH.md code example:

```
# Progress: <Project Name>
# Created: <ISO date>
# Status: [ ] pending  [~] in progress  [x] complete  [-] skipped

## Gates

[ ] Gate 0: Codebase Alignment
[ ] Gate WB: Working Backwards
[ ] Gate 1: Scope Review
[ ] Gate 2: Design Review
[ ] Gate 3: Milestone Review

## Milestones

(none yet)

## Spikes

(none yet)
```

Add a note: `<Project Name>` is derived from the project directory name or user input at bootstrap time. `<ISO date>` is the current date in YYYY-MM-DD format.

**## Greenfield Bootstrap Variant** — When the project is greenfield (empty dir or boilerplate-only per DD-10), Gate 0 is recorded as `[-] Gate 0: Codebase Alignment  Skipped (greenfield)` in the bootstrap template instead of `[ ]`. All other gates remain `[ ]`. This is Claude's discretion per CONTEXT.md.

**## Gate Entry Format** — After approval, a gate entry looks like:
```
[x] Gate 0: Codebase Alignment  Approved: 2026-03-15  docs/codebase-assessment.md
```
Format: `[status] Gate N: Name  Approved: <date>  <artifact-path>` or `[-] Gate N: Name  Skipped` or `[ ] Gate WB: Working Backwards  Pending — offered, awaiting decision`.

**## Milestone Summary Line Format** — One line per milestone in the Milestones section:
```
[ ] Milestone 01: Core Auth  milestones/01-core-auth/  0/3 features complete
```
Format: `[status] Milestone NN: Name  milestones/<NN>-<name>/  N/M features complete`

**## Spikes Section Format** — Per D-02, ALL spikes (open and resolved) appear:
```
[ ] WebSocket Auth Compatibility  docs/spikes/websocket-auth.md
[x] SQLite to Postgres Migration  docs/spikes/sqlite-postgres.md  Resolved: 2026-03-17
```

**## milestone-status.txt Format** — Per-milestone file at `milestones/<NN>-<name>/milestone-status.txt`. Uses same checkbox notation (per STATE-02). Contains:
```
# Milestone 01: Core Auth
# Status: [~] in progress  3 features, 1 complete

## Features

[x] Feature 01.1: User Registration
    Plan: milestones/01-core-auth/plans/user-registration.md
    Sub-features: 3/3 complete

[~] Feature 01.2: Session Management
    Plan: milestones/01-core-auth/plans/session-management.md
    Sub-features: 1/4 complete
    Notes: Switched from JWT to session cookies (see architectural deviation)

[ ] Feature 01.3: Password Reset
    Plan: (not yet planned)
```

**## Write-Ordering Contract** — Per STATE-04: When both `milestone-status.txt` and `progress.txt` need updates, `milestone-status.txt` MUST be written first (source-of-truth-first ordering). This ensures that if a crash occurs mid-write, the more detailed file is already updated and `/project` can detect the divergence on next read. Note: `/project` itself only writes at bootstrap (PROJ-10), so this contract applies to downstream skills (`/build`, `/milestone`, `/plan`). `/project` must document this contract so downstream skills follow it.

**## Parsing Notes** — Instructions for the LLM reading these files:
- Lines starting with `#` are headers or comments
- Status is determined by the bracket marker at the start of each entry line
- Artifact paths follow the date on approved gate entries
- Feature counts in milestone summaries are `N/M` format where N=complete, M=total
- The `Notes:` line on a feature entry is optional

**File 1: `skills/project/references/routing-logic.md`**

Create with these exact sections:

**## Overview** — One paragraph: `/project` determines the next recommended action based on gate states, milestone states, and user intent. This file is the complete routing decision table.

**## Routing Table** — The complete state-to-action table. Expand the excerpt from RESEARCH.md to cover ALL states:

| State | Recommended Action | Alternatives |
|-------|-------------------|--------------|
| No progress.txt | Bootstrap (internal — do not route) | — |
| Gate WB is `[ ] Pending` | Resolve Gate WB: offer Yes/Skip/Defer (per D-08) | — |
| No gates approved (all `[ ]`) | Run `/define` to begin codebase assessment | — |
| Gate 0 approved, Gate WB not offered yet, no working-backwards.md, customer outcome unclear | Offer Gate WB (per D-08, DD-11) | `/define` (continue to Gate 1) |
| Gate 0 approved, Gate WB resolved (`[x]` or `[-]`), no Gate 1 | Run `/define` to continue PRD interview | — |
| Gate 1 approved, no Gate 2 | Run `/design` to create architecture | `/spike` |
| Gate 2 approved, no milestones defined | Run `/milestone` to define first milestone | `/spike` |
| Gate 3 `[~]` in progress, unplanned features exist | Run `/plan` for next unplanned feature | `/milestone` (define another), `/spike` |
| Feature planned (`[~] planned, awaiting build`) | Run `/build` for planned feature | `/plan` (next feature), `/spike` |
| Feature in progress (sub-features partially complete) | Run `/build` to continue feature | `/spike` |
| All features complete in active milestone, more milestones to define | Run `/milestone` for next milestone | `/design` (refresh) |
| All milestones complete | Project complete — celebrate | `/design` (refresh) |
| User says "goals changed" / "revise PRD" / similar | Run `/define` in revision mode (per D-05, PROJ-08) | — |
| User says "re-plan" / "revise milestone" / similar | Run `/milestone` in revision mode (per D-05, PROJ-09) | — |
| Open spikes exist (any state) | `/spike` appears in alternatives when contextually relevant | — |

Note: The "Alternatives" column implements D-04 — only actions valid for the current state appear. Do not show `/plan` if no milestone exists. Do not show `/build` if no planned features exist.

**## Re-planning Intent Detection** — Per D-05, detect natural language keywords:
- PRD revision triggers: "goals changed", "revise PRD", "pivot", "change direction", "update requirements", "scope change"
- Milestone revision triggers: "re-plan", "revise milestone", "regroup features", "change milestone", "re-scope"
- When detected, route to the appropriate skill in revision mode. State the skill name and "in revision mode" explicitly.

**## Gate WB Offer Logic** — Per D-08 and DD-11:
1. Check if `working-backwards.md` exists at `docs/working-backwards.md`
2. Check Gate WB line in progress.txt
3. If Gate WB is `[ ] Pending`: show gentle reminder at top of report, still display full status (per D-09, overrides strict PROJ-07)
4. If no Gate WB line and no `docs/working-backwards.md`: evaluate whether customer outcome is unclear. If unclear, offer Gate WB with 2-3 sentence explanation of Working Backwards value, then `AskUserQuestion` with three options: "Yes" (proceed), "Skip" (record `[-]`), "Defer" (record `[ ] Pending`)
5. If Gate WB is `[x]` or `[-]`: no action needed, proceed with normal routing

**## Artifact Validation** — Per PROJ-04 and DESIGN.md DD-3:
For each gate marked `[x]` in progress.txt, extract the artifact path from the gate entry line. Check if the file exists on disk. If missing, emit an inline warning (per D-06) directly after the gate entry: `Warning: Artifact not found: <path>`. This is informational only — does not block routing.

**## Consistency Validation** — Per PROJ-05 and D-07:
For each milestone in progress.txt, read the corresponding `milestones/<NN>-<name>/milestone-status.txt`. Count `[x]` features in milestone-status.txt. Compare to the `N/M features complete` count in the progress.txt milestone summary line. If they diverge, emit an inline warning after the milestone entry. Per D-07, consistency divergence BLOCKS routing until user acknowledges — this is more severe than missing artifacts.

**## Status Report Structure** — The exact output format the skill produces. Sections in order:

```
GATES:
  [x] Gate 0: Codebase Alignment    Approved: 2026-03-15  docs/codebase-assessment.md
  [-] Gate WB: Working Backwards    Skipped
  [x] Gate 1: Scope Review          Approved: 2026-03-16  prd.md
       Warning: Artifact not found: prd.md
  [x] Gate 2: Design Review         Approved: 2026-03-17  docs/ARCHITECTURE_AND_DESIGN.md
  [~] Gate 3: Milestone Review      In progress
```

4. **ACTIVE MILESTONE section** — Expanded view of the current in-progress milestone with per-feature status:
```
ACTIVE MILESTONE: 01 - Core Auth (2/3 features complete)
  [x] Feature 01.1: User Registration     Complete
  [x] Feature 01.2: Session Management    Complete
  [~] Feature 01.3: Password Reset        In progress
```
Inline consistency warning if milestone-status.txt diverges:
```
  Warning: Milestone status divergence detected — progress.txt says 2/3, milestone-status.txt shows 1/3. Please acknowledge to continue routing.
```

5. **COMPLETED MILESTONES section (conditional)** — One-line summaries for completed milestones:
```
COMPLETED:
  [x] Milestone 01: Core Auth (3/3 features complete)
```

6. **UPCOMING MILESTONES section (conditional)** — One-line summaries for future milestones:
```
UPCOMING:
  [ ] Milestone 02: Dashboard  (0/2 features complete)
```

7. **SPIKES section** — Per D-02, show ALL spikes (open and resolved):
```
SPIKES:
  [x] WebSocket Auth Compatibility    Resolved 2026-03-17
  [ ] SQLite to Postgres Migration    Open
```

8. **RECOMMENDED section** — Per D-03, one bold recommended action plus alternatives:
```
RECOMMENDED: Run `/plan` to create the implementation plan for Feature 01.3: Password Reset
Also available:
  - `/spike` — research a technical question
  - `/milestone` — define the next milestone
```
Per D-04, only show alternatives valid for current state.

**## Empty Project Report** — When only bootstrap has run (all gates pending, no milestones):
```
PROJECT STATUS: <Project Name>

GATES:
  [ ] Gate 0: Codebase Alignment
  [ ] Gate WB: Working Backwards
  [ ] Gate 1: Scope Review
  [ ] Gate 2: Design Review
  [ ] Gate 3: Milestone Review

MILESTONES: (none yet)

SPIKES: (none yet)

RECOMMENDED: Run `/define` to begin project definition
```

**## Blocking Behavior** — Per D-07:
- Missing artifact warnings: informational only, do NOT block routing
- Consistency divergence warnings: BLOCK routing — show the warning and ask user to acknowledge before displaying the RECOMMENDED section
