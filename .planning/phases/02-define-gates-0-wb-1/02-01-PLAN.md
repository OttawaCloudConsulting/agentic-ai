**1. Create gate-0-codebase.md** (Gate 0 full specification per D-01, D-10, D-11):

Structure with these sections:

**`# Gate 0: Codebase Assessment`** -- header with purpose statement: "Scans the existing codebase and produces a structured assessment for use in subsequent gates."

**`## Greenfield Detection (DEF-01)`** -- the heuristic checklist from D-11. ALL of the following must be true to classify as greenfield and skip Gate 0:
- No `src/`, `app/`, or `lib/` directories exist
- No dependency manifests exist (`package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `requirements.txt`, `Gemfile`, `pom.xml`, `build.gradle`)
- Fewer than 5 non-config files (config = README, LICENSE, .gitignore, .editorconfig, .prettierrc, and similar dotfiles)
- Only boilerplate files present (README + license + gitignore pattern)

If ALL conditions are true: skip Gate 0 entirely. Record in progress.txt as `[-] Gate 0: Codebase Alignment  Skipped (greenfield)` and proceed to Gate WB. If ANY condition is false: proceed with Gate 0.

Edge case guidance: monorepos with sparse content should be treated as brownfield (conservative). If uncertain, run Gate 0 -- it's cheaper to scan unnecessarily than to miss existing patterns.

**`## Codebase Scan (DEF-02)`** -- agent-based deep scan per D-10:
- Spawn a sub-agent using the `Agent` tool
- Agent prompt instructs it to read 20-40 files using these selection heuristics:
  - Entry points (main files, index files, app entry points)
  - Configuration files (package.json, tsconfig, webpack, etc.)
  - Test files (sample of test patterns and frameworks used)
  - Key modules (largest files, most-imported files)
  - Git history: `git log --oneline -20` for recent change patterns
  - Directory listing: `ls -R` (first 2 levels) for structure overview
- Agent writes structured findings to a temporary scratch file (e.g., `/tmp/codebase-scan-findings.md`) with sections:
  - Project Overview (language, framework, purpose)
  - File Organization (directory structure, naming patterns)
  - Detected Patterns (code style, architecture patterns, testing approach)
  - Dependency Graph (key dependencies, internal module relationships)
  - Assumptions (things the agent inferred but cannot verify)
  - Patterns That May Need Change (anti-patterns, inconsistencies)
  - Open Questions (things that need user clarification)
  - Recent Changes (from git log)
- Agent uses Read, Bash (for ls, git log), and Glob tools only

**`## Assessment Production (DEF-03)`** -- synthesize agent findings into `docs/codebase-assessment.md`:
- Read the agent's scratch file
- Create `docs/` directory if it doesn't exist (`mkdir -p docs`)
- Write `docs/codebase-assessment.md` with these required sections (per DEF-03):
  1. Project Overview
  2. File Organization
  3. Detected Patterns
  4. Dependency Graph
  5. Assumptions
  6. Patterns to Deviate From
  7. Open Questions
  8. Recent Changes
- The assessment should be factual and specific -- cite file paths, line counts, dependency versions
- Clean up the scratch file after synthesis

**`## Review Phase (DEF-05)`** -- produce-then-review cycle per D-06:
1. Present a summary of the assessment to the user (key findings, patterns detected, open questions)
2. Use `AskUserQuestion` with options: **Approve** / **Revise**
3. If **Revise**: ask what needs changing (D-08: rejection = revision request), apply edits to `docs/codebase-assessment.md`, re-present
4. If **Approve**: proceed to Checklist Validation

**`## Checklist Validation (DEF-04, DEF-06)`** -- per D-07:
1. Generate `docs/reviews/gate-0-review.md` using the Gate 0 section from `references/review-checklist-template.md`
2. Add content-specific `[Auto]` items based on actual assessment content (specific assumptions to verify, specific patterns to confirm)
3. Claude pre-checks items it can verify (file exists, sections present, etc.)
4. Present remaining unchecked items to user for resolution
5. ALL items must be `[x]` or `[-]` (N/A with reason) before proceeding (DEF-06)
6. Create `docs/reviews/` directory if needed (`mkdir -p docs/reviews`)

**`## Gate Approval (DEF-07)`** -- record in progress.txt:
1. Read `references/progress-format.md` for the exact gate entry format
2. Update the Gate 0 line in progress.txt from `[ ] Gate 0: Codebase Alignment` to:
   `[x] Gate 0: Codebase Alignment  Approved: <YYYY-MM-DD>  docs/codebase-assessment.md`
3. Write-ordering: progress.txt is the only file updated here (no milestone-status.txt involved at this gate)

**2. Create gate-wb-working-backwards.md** (Gate WB full specification per D-01, DD-11):

Structure with these sections:

**`# Gate WB: Working Backwards (Optional)`** -- header explaining this is an optional gate that produces a customer-outcome narrative before PRD creation.

**`## Gate WB Offer (DEF-08)`** -- flow control:
- After Gate 0 is complete (or skipped), offer Gate WB
- Use `AskUserQuestion` with 3 options per DD-11:
  - **Yes** -- proceed with Working Backwards exercise
  - **Skip** -- record `[-] Gate WB: Working Backwards  Skipped` in progress.txt and proceed to Gate 1
  - **Defer** -- record `[ ] Gate WB: Working Backwards  Pending — offered, awaiting decision` in progress.txt and proceed to Gate 1
- Include a 2-3 sentence explanation: "Working Backwards starts with the customer experience and works backward to the technical solution. You write a mock press release describing what the customer gets, then FAQ sections that address external and internal questions. This ensures you're solving the right problem before defining scope."

**`## Working Backwards Interview`** -- 2-3 round interview to gather content for PR/FAQ:
- **Round 1 -- Customer and Problem:**
  - Who is the target customer?
  - What problem are they experiencing today?
  - How do they currently solve or work around this problem?
  - What is the measurable outcome they want?
- **Round 2 -- Solution and Experience:**
  - What does the solution look like from the customer's perspective?
  - What is the first thing the customer does with it?
  - What quote would the customer give about this solution?
  - What is the call-to-action (how do they get started)?
- **Round 3 -- Internal Feasibility:**
  - What are the biggest technical risks?
  - What existing systems does this depend on?
  - What is the expected timeline?
  - What would make this project fail?

**`## Document Production (DEF-09)`** -- produce `docs/working-backwards.md`:
- Create the file with these sections:
  1. **Press Release** -- customer-facing narrative: headline, subheading, dateline, problem paragraph, solution paragraph, customer experience paragraph, customer quote, call-to-action
  2. **External FAQ** -- questions a customer would ask (5-8 questions with answers)
  3. **Internal FAQ** -- questions the team would ask about feasibility, timeline, risks (5-8 questions with answers)
- Write the file to `docs/working-backwards.md`

**`## Review Phase (DEF-05 equivalent for WB)`** -- same produce-then-review cycle as Gate 0:
1. Present the Working Backwards document to the user
2. `AskUserQuestion`: **Approve** / **Revise**
3. If **Revise**: ask what needs changing, apply edits, re-present
4. If **Approve**: proceed to Checklist Validation

**`## Checklist Validation (DEF-04, DEF-06)`**:
1. Generate `docs/reviews/gate-wb-review.md` using the Gate WB section from `references/review-checklist-template.md`
2. Add content-specific `[Auto]` items
3. Claude pre-checks, user resolves remaining
4. ALL items must be `[x]` or `[-]` before proceeding

**`## Gate Approval (DEF-08)`** -- record in progress.txt:
- Update Gate WB line to: `[x] Gate WB: Working Backwards  Approved: <YYYY-MM-DD>  docs/working-backwards.md`
- Read `references/progress-format.md` for exact format
