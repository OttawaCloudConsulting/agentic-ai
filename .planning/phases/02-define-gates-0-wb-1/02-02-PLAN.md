Create `skills/project/define/references/gate-1-prd.md` -- the complete Gate 1 specification. This is the most complex reference file. Structure:

**`# Gate 1: Scope Review (PRD)`** -- header with purpose: "Conducts a structured interview and produces a Product Requirements Document (prd.md)."

**`## Context Refresh (DEF-16)`**:
- At the start of Gate 1, silently re-read `docs/codebase-assessment.md` from disk (if it exists)
- Do NOT recap or summarize the assessment to the user -- use it internally as context for the interview
- This mitigates context rot: by Gate 1, the codebase assessment from Gate 0 may have scrolled out of the context window
- If `docs/working-backwards.md` exists (Gate WB was approved), also read it as context (D-14)
- The WB document is context only -- it does NOT auto-populate PRD sections. The full interview still runs, just better informed by the WB narrative.

**`## Interview Rounds (DEF-10)`** -- forked from create-prd interview guide with these changes (per D-13):

- **Round 1 -- Scope and Boundaries** (kept from create-prd Round 1):
  - What is explicitly out of scope? (non-goals)
  - Are there constraints on environments, platforms, or deployment targets?
  - Are there compliance or security requirements?
  - What existing systems or services does this integrate with?

- **Round 2 -- Inputs and Outputs** (was create-prd Round 3, renumbered):
  - What does the consumer or caller configure? (parameters, configuration, inputs)
  - What needs to be exposed or returned? (outputs, endpoints, connection strings)
  - Are there required vs. optional inputs?
  - What validation rules should inputs have?

- **Round 3 -- Security** (was create-prd Round 4, renumbered):
  - What is the encryption strategy (at rest, in transit)?
  - What access control model applies?
  - Are there edge protection or traffic filtering requirements?
  - What security headers or policies are needed?

- **Round 4 -- Operational Concerns** (was create-prd Round 5, renumbered):
  - Is logging needed? (access logs, audit trails)
  - What monitoring/alerting is expected?
  - What is the deployment workflow?
  - Are there cost considerations or constraints?

- **Round 5 -- Milestone Scoping** (NEW, per DD-1):
  - What are the major deliverable milestones? (each should map to a customer-visible outcome)
  - What is the expected ordering of milestones?
  - Are there cross-milestone dependencies?
  - What is the minimum viable first milestone?

**REMOVED:** create-prd Round 2 (Components and Architecture) -- moved entirely to /design per DD-2.
**REMOVED:** Architecture Interview Areas section -- moved entirely to /design.

Interview rules (from create-prd pattern):
- One round at a time -- never dump all questions at once
- 2-4 questions per round via `AskUserQuestion`
- After each round, update `prd.md` and show the user what was added
- Adapt questions to the project type -- skip irrelevant questions
- If Gate WB was used, the interview should reference WB content where relevant (but not skip questions -- D-14)

**`## PRD Production (DEF-11)`**:
- Read `assets/prd-template.md` for the document structure
- After the initial seed question (what are you building, tech stack, primary goal), write `prd.md` with the template structure
- Update `prd.md` after each interview round using the Edit tool
- Milestones section stays as "(to be defined)" -- populated later by /milestone
- Quality bar: specific acceptance criteria language, clear configuration tables, no vague descriptions

**`## Review Phase`** -- produce-then-review per D-06:
1. Present a summary of the complete PRD to the user
2. `AskUserQuestion`: **Approve** / **Revise**
3. If **Revise**: ask what needs changing, apply edits, re-present (D-08)
4. If **Approve**: proceed to Partial Approval Check

**`## Partial Approval (DEF-12)`** -- per D-09:
- When the user approves with reservations, or wants to approve most but revise some sections:
- Present a section checklist (multiSelect) listing each PRD section:
  - [ ] Summary
  - [ ] Goals
  - [ ] Non-Goals
  - [ ] External Dependencies
  - [ ] Milestones
  - [ ] Configuration
  - [ ] Outputs
  - [ ] Risk Assessment
  - [ ] Future Enhancements
- User checks the sections they approve; unchecked sections get focused revision
- For each unchecked section: ask what should change, revise, re-present that section
- Repeat until all sections are checked or user does a full Approve

**`## Checklist Validation (DEF-04, DEF-06)`**:
1. Generate `docs/reviews/gate-1-review.md` using the Gate 1 section from `references/review-checklist-template.md`
2. Add content-specific `[Auto]` items based on actual PRD content
3. Claude pre-checks items it can verify
4. User resolves remaining items
5. ALL items must be `[x]` or `[-]` (N/A with reason) before gate approval

**`## Gate Approval (DEF-13)`**:
1. Read `references/progress-format.md` for exact format
2. Update Gate 1 line in progress.txt to: `[x] Gate 1: Scope Review  Approved: <YYYY-MM-DD>  prd.md`

**`## Revision Mode (DEF-15)`** -- separate section for revision flow:
- Triggered when `/define` detects existing `prd.md` AND user signals revision intent
- Skips Gates 0 and WB entirely -- goes straight to Gate 1 revision
- Steps:
  1. Read existing `prd.md` from disk
  2. Read `docs/codebase-assessment.md` from disk if it exists (same DEF-16 silent re-read)
  3. Ask the user: "What changed?" -- open-ended question about what prompted the revision
  4. Conduct a focused interview on ONLY the affected sections (not the full 5-round interview)
  5. Update `prd.md` with revisions using Edit tool
  6. Present the updated PRD for review (same produce-then-review cycle)
  7. **Surface downstream impacts (per DD-6):** After PRD revision is approved, list all downstream artifacts that MAY need re-review:
     - `docs/ARCHITECTURE_AND_DESIGN.md` (if exists)
     - `milestones/*/README.md` (if any exist)
     - `milestones/*/plans/*.md` (if any exist)
  8. Present this list to the user and ask which (if any) need re-review
  9. Do NOT automatically reset any downstream artifacts -- user decides (DD-6: no automatic cascade)
  10. Record Gate 1 re-approval in progress.txt with updated date
