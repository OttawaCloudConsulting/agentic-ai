**1. `gate-2-design.md` (~150 lines) -- Complete Gate 2 normal-mode specification.**

Structure it identically to `gate-0-codebase.md` with these sections:
- **Input Loading (DES-02, D-07):** Read `prd.md` (required), `docs/codebase-assessment.md` (if exists -- may not for greenfield). Both are primary inputs per D-07.
- **Architecture Agent Scan (D-05, D-06):** Spawn a sub-agent using the `Agent` tool. Agent reads 15-30 files (not 20-40 like Gate 0) through an architecture lens. Agent prompt instructs:
  1. Survey project structure: `ls -R` (first 2 levels), `git log --oneline -20`
  2. Select 15-30 files using architecture-focused heuristics (NOT convention-focused like Gate 0):
     - Component boundaries: module entry points, barrel files, index files
     - Data flow: API routes, event handlers, middleware, database access layers
     - Interface contracts: type definition files, API schemas, shared types
     - Technology choices: config files, dependency manifests, build configs
     - Infrastructure: deployment configs, CI/CD, Dockerfiles
  3. Read each file using Read tool
  4. Write structured findings to `/tmp/architecture-scan-findings.md` with sections: Component Boundaries, Data Flow Patterns, Interface Contracts, Technology Choices, Configuration Patterns
  - Agent tool access: `Read`, `Bash` (for `ls`, `git log`), `Glob` only
  - **Greenfield handling (D-06):** Always spawn the agent even if `docs/codebase-assessment.md` does not exist. For greenfield projects with minimal files, the agent scans whatever exists (configs, dependencies, boilerplate). The synthesis step leans primarily on PRD goals, non-goals, and risk assessment to propose architecture. The reference file must explicitly state: "For greenfield projects, the architecture is driven by the PRD. The agent scan provides whatever context exists."
- **Architecture Document Production (DES-03, D-04):** Synthesize agent findings + PRD into `docs/ARCHITECTURE_AND_DESIGN.md` using `assets/architecture-template.md`. The 6 required sections are: Design Decisions (numbered table with columns: #, Decision, Rationale, Tradeoff, Alternatives Considered), Component Inventory, Data Flow, File Organization, Deployment & Operations, Security Considerations. Create `docs/` directory if needed (`mkdir -p docs`). Clean up scratch file after synthesis.
- **Tradeoff Callouts (D-09):** After presenting the full document, call out 2-4 design decisions with the most significant tradeoffs. Heuristic for detecting key tradeoffs: (a) alternatives are genuinely viable, (b) tradeoff affects multiple components or long-term evolution, (c) reversal would be expensive. Cap at 2-4 to avoid decision fatigue. Present these before the approval checklist.
- **Review Phase (DES-05, DES-06, D-08, D-10):** Produce-then-review cycle:
  1. Present full document summary
  2. Present tradeoff callouts (2-4 key decisions)
  3. `AskUserQuestion` with options: **Approve**, **Revise**, **Partial**
  4. If **Partial** (D-08): multiSelect checklist of the 6 architecture sections. User checks approved sections. Unchecked sections get focused revision with "What should change in [section]?" prompt. Re-present after revision.
  5. If **Revise**: ask what needs changing, apply edits, re-present
  6. If **Approve**: proceed to checklist validation
  - Gate 2 review framing (DD-8): "Here are the technical choices, tradeoffs, component inventory, data flow, and security considerations. Do these align with your constraints? Is anything missing?"
- **Checklist Validation (DES-04, D-11):** Generate `docs/reviews/gate-2-review.md` using `references/review-checklist-template.md`. Include Gate 2 static items + content-specific `[Auto]` items. Claude pre-checks programmatic items. All items must be `[x]` or `[-]` N/A with reason before approval.
- **Gate Approval (DES-07):** Read `references/progress-format.md` for format. Update Gate 2 line in `progress.txt` from `[ ] Gate 2: Design Review` to `[x] Gate 2: Design Review  Approved: <YYYY-MM-DD>  docs/ARCHITECTURE_AND_DESIGN.md`. Only `progress.txt` is updated.

**2. `refresh-mode.md` (~80 lines) -- Complete refresh mode specification (DES-08, D-12, D-13, D-14).**

Sections:
- **Entry Condition:** Refresh mode is entered when Gate 2 is already `[x]` approved AND `docs/ARCHITECTURE_AND_DESIGN.md` exists on disk. SKILL.md detects this in Step 1 and jumps to the refresh step.
- **Deviation Scan (D-12):** Use `Glob` to find all files matching `milestones/*/plans/*.md`. Read each file and search for the `## Architectural Deviations` heading. Extract non-empty deviation entries. For each deviation, also identify the original design decision it modifies (by matching decision number or description in `docs/ARCHITECTURE_AND_DESIGN.md`).
- **Zero Deviations (D-14):** If no non-empty Architectural Deviations sections are found across all plan files, report: "No architectural deviations found. Architecture doc is current." End the session. No revision offer.
- **Per-Deviation Review (D-12):** Present each deviation individually showing: (a) the original design decision from the architecture doc, (b) the deviation description from the feature plan, (c) the reason for the change. After presenting all deviations, use multiSelect to let the user pick which deviations to consolidate into the architecture doc.
- **Consolidation:** Apply selected deviations to `docs/ARCHITECTURE_AND_DESIGN.md`. Update the Design Decisions table with revised decisions. Update other sections as needed (Component Inventory, Data Flow, etc.).
- **Review (D-13):** Present the updated architecture doc using the same section-by-section review flow as normal mode (multiSelect of 6 sections, focused revision on unchecked sections).
- **Gate Update:** Update Gate 2 date in `progress.txt` to reflect the refresh: `[x] Gate 2: Design Review  Approved: <new-date>  docs/ARCHITECTURE_AND_DESIGN.md`
