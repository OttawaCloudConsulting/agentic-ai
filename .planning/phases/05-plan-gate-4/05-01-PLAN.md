**File 2: `skills/project/plan/references/gate-4-plan.md`**

Model on `skills/project/milestone/references/gate-3-milestone.md` (the closest predecessor). The gate-4-plan.md is the self-contained normal-mode specification. Structure it with these sections:

1. **Title and intro paragraph** -- "Produces per-feature implementation plans... This reference contains the complete Gate 4 specification for normal mode -- an executor reading only this file can run the full Gate 4 flow."

2. **Input Loading (PLAN-01)** -- Read primary inputs from disk:
   - `progress.txt` -- required, validate active milestone exists
   - Milestone `README.md` at `milestones/<NN>-<name>/README.md` -- required, primary source of feature details
   - `milestones/<NN>-<name>/milestone-status.txt` -- required, read for feature status
   - `prd.md` -- required, project context
   - `docs/ARCHITECTURE_AND_DESIGN.md` -- required, architecture constraints
   - Spike artifacts per D-11: "Do not auto-detect or auto-scan `docs/spikes/`. Read spike docs ONLY when user explicitly references them."

3. **Milestone and Feature Detection (PLAN-02, D-01, D-02, D-03)** -- Three outcomes:
   - **Auto-detect active milestone (D-02):** Read `progress.txt`, find first milestone at `[ ]` or `[~]` status. User can override with explicit milestone name/number.
   - **Auto-select next unplanned feature (D-01):** Read that milestone's `milestone-status.txt`, find first feature at `[ ]` pending status. Also accept features needing re-plan (features whose plan file exists but user explicitly requests re-plan). User can override with explicit feature name.
   - **No plannable features (D-03):** When all features in the active milestone are `[~]` planned or `[x]` complete, report: "All features in milestone {NN}: {Name} are planned or complete. Run /project to check status." End session.

4. **Codebase Scan Sub-Agent (D-10)** -- Spawn a sub-agent to scan files relevant to the feature being planned. Key instructions for the sub-agent prompt:
   - Read the feature's acceptance criteria from milestone README
   - Identify files that the feature will likely touch (by name patterns, directory structure, imports)
   - Read 5-15 files relevant to this specific feature (NOT architecture-wide -- that was /design's job)
   - Return: file inventory, relevant code patterns, existing interfaces, integration points
   - This is narrower than /design's 15-30 file architecture scan

5. **Plan Generation (PLAN-03)** -- Generate `milestones/<NN>-<name>/plans/<feature-slug>.md` using `assets/feature-plan-template.md`. Feature slug is kebab-case derived from the feature name (e.g., "User Registration" -> `user-registration.md`). Populate all 12 sections using information from:
   - Milestone README (acceptance criteria, feature description)
   - PRD (project context, goals, non-goals)
   - Architecture doc (component inventory, design decisions, data flow)
   - Sub-agent scan results (files to modify, existing interfaces, integration points)

6. **Sub-Feature Sizing Validation (PLAN-04, D-06, D-07)** -- After generating the plan, evaluate each sub-feature:
   - Heuristic estimation per D-06: estimate complexity based on files to touch, logic scope, and integration surface against the ~120k-token guideline
   - If any sub-feature appears oversized per D-07: flag it inline, propose 2-3 smaller sub-features, include the revised list in the plan presented to the user
   - No hard metric or token counting -- this is a judgment call

7. **Tradeoff Callouts (PLAN-07, D-13)** -- Before presenting for review, identify 1-2 key tradeoff callouts:
   - Most significant approach decisions (e.g., "Using X pattern because Y, alternative Z was considered")
   - Most significant sizing decisions (e.g., "SF-3 is the largest sub-feature -- could be split further but kept together for atomicity")
   - Lighter than /design's 2-4 callouts since plans are narrower in scope

8. **Review Phase (PLAN-07, PLAN-08, D-12)** -- Whole-plan approve/revise pattern:
   - Present the complete plan to the user
   - Present the 1-2 tradeoff callouts
   - Use `AskUserQuestion` with options: **Approve** / **Revise**
   - If **Revise**: ask "What should change?", apply edits to the plan using the Edit tool, re-present. Repeat until approved.
   - This is simpler than section-by-section (used in /design and /milestone) because plans are single-feature scope

9. **Review Checklist Generation (PLAN-05)** -- Generate `milestones/<NN>-<name>/reviews/gate-4-<feature-slug>-review.md` using `references/review-checklist-template.md`. The feature slug in the filename matches the plan file slug.

10. **Checklist Validation (PLAN-05)** -- Claude pre-checks items it can verify programmatically:
    - Plan file exists at expected path
    - All 12 required sections present in the plan
    - milestone-status.txt exists
    - Feature exists in milestone-status.txt
    Present remaining unchecked items to user. All items must be `[x]` or `[-]` N/A with reason before approval.

11. **State File Updates (PLAN-06, PLAN-09)** -- Two-phase update:
    - **On plan creation (PLAN-06):** Update the feature's `Plan:` line in `milestone-status.txt` from `(not yet planned)` to the plan file path (e.g., `milestones/01-core-auth/plans/user-registration.md`)
    - **On Gate 4 approval (PLAN-09):** Update the feature marker in `milestone-status.txt` from `[ ]` to `[~] planned, awaiting build`. Also add `Sub-features: 0/N complete` line.
    - **CRITICAL: /plan does NOT write to progress.txt.** Unlike /milestone which writes to both state files, /plan writes ONLY to milestone-status.txt. Gate 4 is a feature-level event, not a milestone-level event.
    - Follow the exact format from `references/progress-format.md` for milestone-status.txt entries.

12. **Next Feature Offer (D-14)** -- After Gate 4 approval: "Feature {X} planned. Next unplanned feature: {Y}. Plan it now?" User can continue (return to step 3 with next feature) or exit.

Key anti-patterns to document in the reference:
- "NEVER write to progress.txt -- /plan writes ONLY to milestone-status.txt"
- "Do NOT check for [x] Gate 3 -- Gate 3 stays [~] In progress. Validate that an active milestone exists instead."
- "Do NOT auto-scan spike artifacts -- read ONLY when user explicitly references them (D-11)"

**File 1: `skills/project/plan/references/revision-mode.md`**

Adapt from `skills/project/milestone/references/revision-mode.md` for feature-plan scope. Key differences from /milestone revision mode:

Title: "# Revision Mode: Feature Re-Plan"

Sections:

1. **Entry Condition (D-04)** -- Re-plan mode is entered when the target feature already has a plan file on disk. SKILL.md auto-detects this by checking whether `milestones/<NN>-<name>/plans/<feature-slug>.md` exists. If the plan file does not exist, this is not re-plan mode.

2. **Load Existing Plan (D-05)** -- Read the existing feature plan from disk: `milestones/<NN>-<name>/plans/<feature-slug>.md`. Also read `milestones/<NN>-<name>/README.md` for current acceptance criteria and `milestones/<NN>-<name>/milestone-status.txt` for current feature status.

3. **Diff-Focused Interview (D-05)** -- Ask "What changed?" to understand the nature of the re-plan. Do NOT discard and regenerate the entire plan. Common change types:
   - Acceptance criteria changed (from milestone revision)
   - Approach needs revision (implementation discovery)
   - Sub-feature sizing wrong (too large or too small)
   - New edge cases discovered
   - Dependencies changed
   - Interface contracts need updating

4. **Targeted Revision (D-05)** -- Revise ONLY affected sections using the Edit tool:
   - If acceptance criteria changed: update Acceptance Criteria section
   - If approach changed: update Approach, Sub-Features, and Files to Create/Modify sections
   - If sub-features changed: update Sub-Features section, re-validate sizing
   - If edge cases discovered: update Edge Cases section
   - If dependencies changed: update Dependencies section
   - If interfaces changed: update Interface Contracts section
   - Preserve unaffected sections exactly as they are

5. **Review** -- Present the revised plan using the same whole-plan Approve/Revise pattern as normal mode (D-12). Highlight what changed vs what was preserved. Generate a fresh `gate-4-<feature-slug>-review.md` checklist -- the prior review is no longer valid after re-planning.

6. **State File Updates** -- If the feature was previously at `[~] planned, awaiting build`:
   - Reset to `[ ]` pending in milestone-status.txt (the plan has changed, needs re-approval)
   - After re-approval: update back to `[~] planned, awaiting build`
   - If sub-feature count changed: update `Sub-features: 0/N complete` line
   - CRITICAL: Do NOT write to progress.txt
