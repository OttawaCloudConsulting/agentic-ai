**File 1: `build-execution.md`** -- The main build execution specification. This is the largest reference file. Structure it as a self-contained spec that an executor reading only this file can run the complete sub-feature build loop. Include these sections:

1. **Prerequisite Validation (BUILD-01):** Read `milestone-status.txt` for the target feature. Feature must be at `[~] planned, awaiting build` status with a plan file path. If no planned features exist, report: "No Gate 4-approved plans found. Run /plan to create a feature plan first." and stop.

2. **Feature Plan Loading (per D-01):** Read the feature plan from the path in `milestone-status.txt`. Parse the Sub-Features checklist. Find the first `[ ]` (unchecked) sub-feature. If all are `[x]`, skip to Feature Completion section. This is the auto-resume mechanism.

3. **Sub-Feature Execution Loop (BUILD-03, BUILD-04, D-01, D-03, D-04):** For each unchecked sub-feature in order:
   - Read the sub-feature description from the plan
   - Implement the sub-feature (the actual code writing -- this is the user's codebase, /build writes real code)
   - When implementation diverges from plan or architecture doc, follow the deviation recording spec in `references/deviation-recording.md` (D-11, D-13)
   - Commit the sub-feature with message format: `feat(<feature-slug>): SF-N <sub-feature-name>` (D-03)
   - Mark the sub-feature `[x]` in the feature plan using Edit tool (BUILD-04)
   - Update `milestone-status.txt`: increment the `Sub-features: N/M complete` count (BUILD-08)
   - Display checklist recap: show the full Sub-Features checklist with current `[x]`/`[ ]` marks and announce the next sub-feature (D-04)
   - Continue to next `[ ]` sub-feature, or proceed to Feature Completion if all done

4. **Feature Completion (BUILD-05, BUILD-08, BUILD-09, D-08, D-09):** After all sub-features are `[x]`:
   - Run the feature's Test Command from the plan (BUILD-05, D-08). Execute via Bash tool with reasonable timeout.
   - **If test passes (exit code 0):**
     - Update `milestone-status.txt` FIRST (STATE-04): change feature from `[~]` to `[x]`, set `Sub-features: N/N complete`, add `Completed: <ISO date>` to Notes (BUILD-08)
     - Update `progress.txt` SECOND: increment the feature count in the milestone summary line (e.g., `2/3` becomes `3/3`) (BUILD-09)
     - **If this was the last feature** (completed count equals total count): also change the milestone marker from `[~]` to `[x]` in `progress.txt` (BUILD-09)
   - **If test fails (non-zero exit code, per D-09):** Hard stop. Display:
     ```
     TEST FAILED: <feature plan path>
     
     Command: <test command>
     Exit code: <code>
     
     Output:
     <full test output>
     
     DIAGNOSIS: <Claude's analysis of why the test failed>
     
     Options:
     - Fix       -- Fix the code to match test expectations
     - Update    -- Provide a corrected test command
     - Exit      -- Stop here; investigate manually
     ```
     Use `AskUserQuestion` with these 3 options (max 12-char headers: Fix, Update, Exit).
     - **Fix:** Claude diagnoses and fixes the code, re-runs test. If pass, proceed with completion. If fail again, show failure output and re-offer options.
     - **Update (BUILD-06, D-10):** User provides corrected test command. Claude writes it to the feature plan's Test Command section using Edit tool. Re-runs the updated command.
     - **Exit:** Stop. Sub-features already marked `[x]` are preserved. User investigates manually. Next `/build` invocation will skip to Feature Completion since all sub-features are done.

5. **State File Update Details:** Reference `references/progress-format.md` for exact formats. The write-ordering contract (STATE-04) is critical: `milestone-status.txt` is ALWAYS written before `progress.txt`. This ensures crash safety -- if interrupted mid-write, the more detailed file is already correct and `/project` can detect divergence.

6. **Commit Message Format:** `feat(<feature-slug>): SF-N <sub-feature-name>` where `<feature-slug>` is derived from the feature plan filename (e.g., `session-management` from `session-management.md`).

7. **Session Continuity (D-02):** If context window is filling up, mark all completed sub-features `[x]` in the plan, commit, update `milestone-status.txt`. The plan checklist IS the continuity mechanism. Next `/build` invocation auto-resumes from first unchecked item.

**File 2: `codebase-refresh.md`** -- Incremental codebase assessment refresh specification. Structure:

1. **Timing (D-06, D-07):** This runs BEFORE reading the feature plan. Order: refresh assessment -> commit assessment -> then load feature plan and begin build.

2. **Incremental Refresh Strategy (D-05, BUILD-02):** 
   - Detect last assessment date: `git log -1 --format="%ai" -- docs/codebase-assessment.md`. If no commit found (first build after /define), fall back to scanning commits from the last 7 days.
   - Find changed files: `git log --since="<last-assessment-date>" --name-only --format="" | sort -u`
   - If no files changed since last assessment: skip refresh, report "Codebase assessment is current (no changes since <date>)."

3. **Sub-Agent Prompt:** Spawn an Agent tool sub-agent with instructions to:
   - Read `docs/codebase-assessment.md` (current state)
   - Read only the changed/new files identified above (NOT a full re-scan)
   - Update the Recent Changes section with new entries
   - Update any other sections affected by the changes (File Organization, Detected Patterns, Dependency Graph)
   - Preserve all existing assessment content that remains accurate
   - Write the updated assessment back to `docs/codebase-assessment.md`
   - The sub-agent uses Read, Write, Bash, and Glob tools

4. **Standalone Commit (D-07):** After the sub-agent completes, commit the updated assessment: `docs(assessment): refresh codebase assessment for <feature-name>`. This commit is separate from any implementation commits.

5. **Edge Cases:**
   - `docs/codebase-assessment.md` doesn't exist: Report "No codebase assessment found. Run /define to create one." This is a warning, not a blocker -- /build can proceed without it, but the user should know.
   - Assessment file exists but was never committed: Fall back to 7-day scan window.

**File 1: `deviation-recording.md`** -- Architectural deviation detection and recording specification. Structure:

1. **What Constitutes a Deviation (D-11):** A deviation occurs when the implementation CONTRADICTS what the feature plan or `docs/ARCHITECTURE_AND_DESIGN.md` specifies. A deviation is NOT:
   - Adding implementation detail the plan didn't specify (plans describe intent, not exact code)
   - Using a slightly different API or method name than implied by the plan
   - Making reasonable implementation choices within the plan's described approach
   A deviation IS:
   - Using a fundamentally different approach than the plan specified (e.g., session cookies instead of JWT)
   - Skipping a component the plan said to create
   - Adding a component the plan said was unnecessary
   - Changing the data model or interface contracts from what the plan specified

2. **Detection and Confirmation Flow (D-11):** When Claude detects a deviation during sub-feature implementation:
   - Pause implementation
   - Present to user: "This deviates from the plan because X. Record as deviation?"
   - Use `AskUserQuestion` with options: **Record** (confirm and write), **Dismiss** (not a real deviation, continue)
   - If the user dismisses, continue implementation without recording

3. **Structured 4-Field Entry (D-12):** Each confirmed deviation is written to the feature plan's `## Architectural Deviations` section in this exact format:
   ```markdown
   ### Deviation N: <brief title>
   - **What changed:** <what the implementation actually does>
   - **Originally planned:** <what the plan or architecture doc specified>
   - **Why necessary:** <why the change was required>
   - **Impact:** <effect on other components or future work>
   ```
   The deviation number auto-increments from existing entries in the section. If the section currently says `(none)`, replace it with the first deviation entry.

4. **Immediate Write (D-13):** Write the deviation entry to the feature plan using the Edit tool as soon as the user confirms it. The deviation gets committed with the sub-feature that caused it. This ensures deviations are never lost even if the session ends unexpectedly.

5. **Deviation Count:** After writing a deviation, if the feature accumulates 3+ deviations, add a note: "Multiple deviations detected. Consider running /design in refresh mode after this feature completes to consolidate architectural changes."
