**research-agent.md** -- Research Sub-Agent Specification

Structure (follow gate-2-design.md pattern):
1. Title: "# Research Agent Specification"
2. Overview paragraph: Spawned by /spike SKILL.md to investigate a user-defined research question using available tooling. Writes structured findings to a temp file for red-team review. Per D-01, runs first before the red-team agent.
3. "## Input" section: The research agent receives two inputs from the parent SKILL.md:
   - `research_question` -- the user's question (verbatim from SPIKE-01)
   - `available_tooling` -- list of tools/libraries to evaluate (verbatim from SPIKE-01)
4. "## Agent Prompt" section: Instruct the agent to:
   - Read the research question and available tooling list
   - Develop a methodology: break the question into sub-questions, identify what needs investigation
   - For each tool/library in the available tooling list: check current version, compatibility, documentation quality, community activity, known issues
   - Use web search (WebFetch) for documentation, release notes, compatibility info
   - Use codebase tools (Read, Glob, Grep, Bash) to check existing project patterns if relevant
   - Write structured findings to `/tmp/spike-research-findings.md` with sections: Question Restated, Methodology, Per-Tool Analysis (one subsection per tool), Comparison Matrix (if multiple tools), Findings Summary, Open Questions
5. "## Agent Tool Access" section: The agent uses: Read, Bash, Glob, Grep, WebFetch. These tools allow documentation lookup, codebase scanning, and version checking.
6. "## Output" section: Agent writes to `/tmp/spike-research-findings.md`. The parent SKILL.md reads this file after agent completion.
7. "## Edge Cases" section:
   - No tooling listed: Agent researches the question broadly without tool-specific analysis
   - Ambiguous question: Agent restates the question with its interpretation and proceeds
   - Web search unavailable: Agent falls back to codebase analysis and documented knowledge

**redteam-agent.md** -- Red-Team Sub-Agent Specification

Structure (follow gate-2-design.md pattern):
1. Title: "# Red-Team Agent Specification"
2. Overview paragraph: Spawned by /spike SKILL.md after the research agent completes. Reads research findings and independently validates them. Per D-01, runs second. Per D-03, has full tooling access to independently verify claims. Per D-04, challenges factual errors, missing alternatives, flawed reasoning, unverified assumptions, version/compatibility issues.
3. "## Input" section: The red-team agent receives:
   - `/tmp/spike-research-findings.md` -- the research agent's output
   - `research_question` -- the original question (for context)
   - `available_tooling` -- the original tooling list (for context)
4. "## Agent Prompt" section: Critical instruction -- **adversarial posture**. The agent's job is to find flaws, not confirm findings. Instruct the agent to:
   - Read the research findings thoroughly
   - For each claim in the findings: attempt to verify or disprove using independent sources
   - Check for: factual errors (wrong versions, deprecated APIs, incorrect syntax), missing alternatives (tools/approaches the research agent didn't consider), flawed reasoning (non-sequiturs, correlation-as-causation, survivorship bias), unverified assumptions (claims stated as fact without evidence), version/compatibility issues (works on version X but project uses version Y)
   - Use web search to independently verify key claims -- do NOT rely solely on the research agent's sources
   - Write structured critique to `/tmp/spike-redteam-findings.md` with sections: Assessment Summary (overall quality rating: thorough/adequate/incomplete/flawed), Factual Errors (numbered list, each with: claim, evidence of error, correction), Missing Alternatives (tools/approaches not considered), Reasoning Issues (numbered list with claim and counter-argument), Unverified Assumptions (claims needing evidence), Version/Compatibility Concerns, Strengths (what the research got right)
   - Include a "Strengths" section to acknowledge what the research got right -- red-team is adversarial but fair
5. "## Agent Tool Access" section: The agent uses: Read, Bash, Glob, Grep, WebFetch. Same broad access as research agent per D-03, enabling independent verification.
6. "## Output" section: Agent writes to `/tmp/spike-redteam-findings.md`. The parent SKILL.md reads this file after agent completion.
7. "## Confirmation Bias Prevention" section (per RESEARCH.md Pitfall 1):
   - The prompt explicitly states "your job is to find flaws, not confirm"
   - The agent has independent tool access -- it does NOT need to trust the research agent's sources
   - The output structure forces the agent to enumerate specific issues rather than giving a general "looks good"
   - If the agent finds zero issues, it must explicitly state "No issues found after independent verification of N claims" -- forcing it to quantify its verification effort

**spike-format.md** -- Spike Artifact Template and Section Specification

Structure:
1. Title: "# Spike Artifact Format"
2. Overview: Defines the structure of spike artifacts produced at `docs/spikes/<topic>.md`. Per D-09, all spike artifacts use the same fixed section structure. Per D-10, the Red-Team Assessment is an equal peer section at the same level as Findings -- the two perspectives are never merged or suppressed.
3. "## Topic Slug Generation" section: Convert the spike topic to a filename-safe slug: lowercase, spaces to hyphens, strip special characters (keep alphanumeric and hyphens only), trim leading/trailing hyphens. Example: "WebSocket Auth Compatibility" becomes "websocket-auth-compatibility". This is consistent with milestone and feature slug patterns in the project.
4. "## New Spike Template" section: The exact markdown template for a new spike artifact:

```markdown
# Spike: <Topic Name>

## Question
<The specific technical question or hypothesis provided by the user>

## Available Tooling
<The tools/libraries/approaches the user listed for evaluation>

## Methodology
<What the research agent investigated and how -- methodology from research findings>

## Findings
<Research agent's discoveries, organized by sub-question or theme -- from /tmp/spike-research-findings.md>

## Red-Team Assessment
<Red-team agent's critique -- from /tmp/spike-redteam-findings.md. This is an EQUAL PEER section to Findings. Do not merge, summarize, or suppress any red-team concerns.>

## Recommendation
<Clear pick with rationale per D-11. States the recommended approach, why it is recommended, what risks remain after red-team review, and conditions under which the recommendation should be revisited.>

## Status
open

## Follow-Up Log
(no follow-ups yet)
```

5. "## Follow-Up Log Entry Format" section: Per D-08 and D-12, each follow-up appends a dated entry with full findings and red-team assessment. The entry format:

```markdown
### Follow-Up: YYYY-MM-DD — <Follow-up question>

#### Findings
<New research findings for this follow-up question>

#### Red-Team Assessment
<New red-team critique for this follow-up's findings>

#### Updated Recommendation
<Whether the original recommendation changes based on new information>
```

Per RESEARCH.md Pitfall 2: Follow-up mode must READ the existing spike artifact, APPEND to the Follow-Up Log section replacing "(no follow-ups yet)" if present, and preserve all original content. Never overwrite the original findings.

6. "## Assembly Instructions" section: How the parent SKILL.md assembles the final artifact:
   - Read `/tmp/spike-research-findings.md` for Methodology and Findings sections
   - Read `/tmp/spike-redteam-findings.md` for Red-Team Assessment section
   - Write Recommendation section by synthesizing both: state the pick, incorporate red-team feedback, note remaining risks
   - Set Status to "open"
   - Set Follow-Up Log to "(no follow-ups yet)"

7. "## Resolution" section: Per D-07 and SPIKE-06, when user signals resolution:
   - Change `## Status` from "open" to "resolved"
   - Update progress.txt spike entry from `[ ]` to `[x]` with `Resolved: YYYY-MM-DD` suffix
