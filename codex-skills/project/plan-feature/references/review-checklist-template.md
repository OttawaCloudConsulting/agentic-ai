# Gate Review Checklist Template

This is the review format for `$project-plan-feature` gate reviews (Gate 4). The gate generates a review checklist file using this template structure, with gate-specific static items below and content-specific items auto-generated by Codex based on actual plan content.

## File Header

Every review checklist file begins with this header:

```
# Gate 4 Review -- Feature Plan: {Feature Name}

**Artifact:** milestones/<NN>-<name>/plans/<feature-slug>.md
**Status:** [ ] Pending
**Reviewer(s):**
**Date:**
```

## Checklist Structure

Each review checklist has two tiers of items:

1. **Static items** (from this template): Baseline checklist items that always appear for Gate 4. These are defined in the gate-specific section below.

2. **Content-specific items** (auto-generated by Codex): Items added based on actual plan content. These appear after the static items and are prefixed with `[Auto]`. Examples: specific sub-features to verify sizing, specific interfaces to validate, specific dependencies to confirm.

Format:

```
## Checklist

- [ ] Static item from template
- [ ] Static item from template
- [ ] [Auto] Content-specific item based on plan
- [ ] [Auto] Content-specific item based on plan
```

## Gate 4: Feature Implementation Plan -- Static Items

These items always appear in `milestones/<NN>-<name>/reviews/gate-4-<feature-slug>-review.md`:

- `[ ] Does the approach handle known edge cases?`
- `[ ] Are the sub-features correctly scoped for single-session work?`
- `[ ] Is the test command appropriate for this feature?`
- `[ ] Are the files to create/modify correct?`
- `[ ] Are interface contracts compatible with existing code?`

## Content-Specific [Auto] Items

Codex generates content-specific items based on the actual `milestones/<NN>-<name>/plans/<feature-slug>.md` content. These items are prefixed with `[Auto]` and target specific elements of the feature plan. Examples:

- `[ ] [Auto] Verify sub-feature: "{SF name}" fits within ~120k token session`
- `[ ] [Auto] Confirm interface: "{interface}" matches existing codebase pattern`
- `[ ] [Auto] Check dependency: "{dependency}" is available/accessible`
- `[ ] [Auto] Validate test command: "{command}" exercises the acceptance criteria`
- `[ ] [Auto] Confirm edge case: "{edge case}" is handled in approach section`
- `[ ] [Auto] Verify file: "{path}" exists or can be created at expected location`

The number of `[Auto]` items depends on the complexity of the feature plan. Aim for 2-6 auto-generated items that target the most critical or nuanced aspects of the plan.

## Completion Rules

All checklist items must be resolved before the feature plan review is considered complete:

- **`[x]`** -- Verified: Item has been reviewed and confirmed correct.
- **`[-]`** -- N/A with reason: Item does not apply to this feature plan. A brief reason must follow (e.g., `[-] No external dependencies -- self-contained feature`).

No item may be left as `[ ]` at approval time. Every item must reach `[x]` (verified) or `[-]` (N/A with reason).

**Pre-check process:**

1. Codex pre-checks items it can verify programmatically (e.g., plan file exists, all 12 sections present, milestone-status.txt exists, feature exists in milestone-status.txt).
2. Codex presents remaining unchecked items to the user for review and resolution.
3. User marks each remaining item as `[x]` or `[-]` with reason.
4. Feature plan review is recorded as approved only after all items are resolved.

## Reviewer Comments

Each review checklist ends with a comments section:

```
## Reviewer Comments

(none)
```
