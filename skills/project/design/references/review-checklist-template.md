# Gate Review Checklist Template

This is the review format for `/design` gate reviews (Gate 2). The gate generates a review checklist file using this template structure, with gate-specific static items below and content-specific items auto-generated by Claude based on actual artifact content.

## File Header

Every review checklist file begins with this header:

```
# Gate {N} Review -- {Gate Name}

**Artifact:** {path to primary artifact}
**Status:** [ ] Pending
**Reviewer(s):**
**Date:**
```

## Checklist Structure

Each review checklist has two tiers of items:

1. **Static items** (from this template): Baseline checklist items that always appear for Gate 2. These are defined in the gate-specific section below.

2. **Content-specific items** (auto-generated by Claude): Items added based on actual artifact content. These appear after the static items and are prefixed with `[Auto]`. Examples: specific design decisions to verify, specific components to confirm, specific security measures to validate.

Format:

```
## Checklist

- [ ] Static item from template
- [ ] Static item from template
- [ ] [Auto] Content-specific item based on artifact
- [ ] [Auto] Content-specific item based on artifact
```

## Gate 2: Design Review -- Static Items

These items always appear in `docs/reviews/gate-2-review.md`:

- `[ ] Are the design decisions sound? Are tradeoffs acceptable?`
- `[ ] Is the component inventory complete?`
- `[ ] Does the data flow match your understanding of the system?`
- `[ ] Are there security considerations missing?`

## Content-Specific [Auto] Items

Claude generates content-specific items based on the actual `docs/ARCHITECTURE_AND_DESIGN.md` content. These items are prefixed with `[Auto]` and target specific elements of the architecture document. Examples:

- `[ ] [Auto] Verify decision: "{specific decision from Design Decisions table}"`
- `[ ] [Auto] Confirm component: "{component name}" interfaces are complete`
- `[ ] [Auto] Review data flow: "{specific flow}" covers error cases`
- `[ ] [Auto] Validate security: "{specific security measure}" is sufficient`

The number of `[Auto]` items depends on the complexity of the architecture document. Aim for 2-6 auto-generated items that target the most critical or nuanced aspects of the design.

## Completion Rules

All checklist items must be resolved before gate approval can be recorded:

- **`[x]`** -- Verified: Item has been reviewed and confirmed correct.
- **`[-]`** -- N/A with reason: Item does not apply to this project/artifact. A brief reason must follow (e.g., `[-] No deployment config -- local-only tool`).

No item may be left as `[ ]` at approval time. Every item must reach `[x]` (verified) or `[-]` (N/A with reason).

**Pre-check process:**
1. Claude pre-checks items it can verify programmatically (e.g., file exists, required sections present, tables populated).
2. Claude presents remaining unchecked items to the user for review and resolution.
3. User marks each remaining item as `[x]` or `[-]` with reason.
4. Gate approval is recorded only after all items are resolved.

## Reviewer Comments

Each review checklist ends with a comments section:

```
## Reviewer Comments

(none)
```
