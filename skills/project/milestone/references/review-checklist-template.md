# Gate Review Checklist Template

This is the review format for `/milestone` gate reviews (Gate 3). The gate generates a review checklist file using this template structure, with gate-specific static items below and content-specific items auto-generated by Claude based on actual milestone content.

## File Header

Every review checklist file begins with this header:

```
# Gate 3 Review -- Milestone Planning

**Artifact:** milestones/<NN>-<name>/README.md
**Status:** [ ] Pending
**Reviewer(s):**
**Date:**
```

## Checklist Structure

Each review checklist has two tiers of items:

1. **Static items** (from this template): Baseline checklist items that always appear for Gate 3. These are defined in the gate-specific section below.

2. **Content-specific items** (auto-generated by Claude): Items added based on actual milestone content. These appear after the static items and are prefixed with `[Auto]`. Examples: specific features to verify sizing, specific dependencies to confirm ordering, specific acceptance criteria to validate.

Format:

```
## Checklist

- [ ] Static item from template
- [ ] Static item from template
- [ ] [Auto] Content-specific item based on milestone
- [ ] [Auto] Content-specific item based on milestone
```

## Gate 3: Milestone Planning -- Static Items

These items always appear in `milestones/<NN>-<name>/reviews/gate-3-review.md`:

- `[ ] Does the milestone represent a coherent, deployable increment?`
- `[ ] Are features correctly grouped? Any that belong in a different milestone?`
- `[ ] Is the ordering correct given dependencies?`
- `[ ] Are the acceptance criteria specific and testable?`
- `[ ] Is the sizing realistic?`

## Content-Specific [Auto] Items

Claude generates content-specific items based on the actual `milestones/<NN>-<name>/README.md` content. These items are prefixed with `[Auto]` and target specific elements of the milestone definition. Examples:

- `[ ] [Auto] Verify feature: "{feature name}" has specific acceptance criteria`
- `[ ] [Auto] Confirm sizing: "{feature name}" fits 2-5 sub-features`
- `[ ] [Auto] Check dependency: "{feature A}" correctly ordered before "{feature B}"`
- `[ ] [Auto] Validate scope: "{feature name}" delivers user-visible value (not internal refactoring)`
- `[ ] [Auto] Confirm milestone: all features together form a deployable increment`

The number of `[Auto]` items depends on the complexity of the milestone. Aim for 2-6 auto-generated items that target the most critical or nuanced aspects of the milestone definition.

## Completion Rules

All checklist items must be resolved before the milestone review is considered complete:

- **`[x]`** -- Verified: Item has been reviewed and confirmed correct.
- **`[-]`** -- N/A with reason: Item does not apply to this milestone. A brief reason must follow (e.g., `[-] No dependencies -- first milestone`).

No item may be left as `[ ]` at approval time. Every item must reach `[x]` (verified) or `[-]` (N/A with reason).

**Pre-check process:**
1. Claude pre-checks items it can verify programmatically (e.g., README.md exists, required sections present, milestone-status.txt exists with correct feature count).
2. Claude presents remaining unchecked items to the user for review and resolution.
3. User marks each remaining item as `[x]` or `[-]` with reason.
4. Milestone review is recorded as approved only after all items are resolved.

## Reviewer Comments

Each review checklist ends with a comments section:

```
## Reviewer Comments

(none)
```
