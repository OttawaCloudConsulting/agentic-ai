# Red-Team Report: `OPTIONS_ANALYSIS.md` — Sandboxed Agent Containerization

## Executive Summary

Four reviewers, each working a different published standard end to end, converged independently on the same structural verdict: `OPTIONS_ANALYSIS.md` names indirect prompt injection as its primary threat (L32) and then designs exclusively against the network consequences of a successful injection. None of the three options contains a control that acts on the threat itself. Three of the four reviewers reached that conclusion through entirely different control families — Five Eyes input management, CIS 9.3/9.6/10.1 content inspection, CIS 16.10/16.11 context-boundary enforcement — and the fourth reached a sharper version of it: the dominant local MCP transport (stdio) never crosses any of the three options' enforcement points at all, so the vector the threat model names is not merely unmitigated but unobserved. The document's own framing sentence at L37 — "This is the single axis on which the three options differ" — is what produces this, and its own 11-row comparison table refutes it.

The second theme is that the comparison table at L152–166, which the document declares to be the decision material (L5), overstates the design on four separate axes: audit coverage (network destinations only, but scored "Full, self-owned" and used as one of four reasons to select Option 2 at L227), cross-agent isolation (`internal: true` removes the default route but does not stop container-to-container traffic, so "Per container" is a filesystem claim presented as a network one), vendor dependency ("None" for Options 2 and 3 while all three depend entirely on three SaaS model providers), and MCP coverage (absent from every row). Separately, the credential brokering that the recommendation is built around is specified with no caller identity at the mediator — turning it on makes cross-agent credential isolation strictly worse than the volume separation it replaces, and it is the artifact's own headline argument for the option it selects. The document is preventive-only: it builds a detection surface and defines no response, no revocation path, no rollback, and no adversarial test of the boundary it commits to building by hand.

**Overall risk:** Critical
**Total findings:** 28 (Critical: 4, High: 12, Medium: 10, Low: 2)

## Critical & High Findings

### Finding 1: The stated primary threat has no mitigating control in any of the three options
- **Severity:** Critical
- **Lens(es):** CIS v8.1 AI and LLM Companion Guide (F1) · Five Eyes (F2) · CIS v8.1 AI Agents Companion Guide (F7)
- **Observation:** L32 names the primary threat precisely — "indirect prompt injection from a repository, a web page, an MCP server response, or a dependency". L34 then states "That threat model has two consequences that drive every option below", and both consequences (L36–37) are about egress. Every control in all three options sits downstream of compromise. There is no control at any of the four ingress points the artifact itself enumerates, and no control at the application layer where the injection is interpreted.
- **Evidence:**
  - The strings `system prompt`, `context`, `guardrail` and `output` occur zero times in all 236 lines (CIS AI/LLM).
  - L104 is the only claim of layered defence: "Each agent's own native controls are layered inside as defence in depth: `srt` for Claude Code, `features.network_proxy` for Codex, `agy --sandbox` for Antigravity." All three are containment primitives; none inspects an input — and all three are reachable by the agent process, which L37 itself classifies as "not a control".
  - Five Eyes L519–525 (input management): "Implement robust input validation and sanitisation for all agent inputs"; "Integrate prompt injection filters and semantic analysis to detect malicious instructions." L711–712: "Validate tool responses to prevent malicious or unsafe instructions." L326–327: "Two-way tool integration allows tools to send potentially arbitrary instructions back to the LLM" — the mediator sits directly on that return path in Option 2 and the artifact never proposes using it.
  - CIS AI/LLM §16.10 (6295–6304): "Enforce strict architectural separation between privileged system instructions and untrusted inputs or retrieved data… treat system prompts as immutable code… the system must default to a 'deny' state." §16.11 (6310–6316): "Implement vetted, code-based safety frameworks… rather than relying solely on system prompts or natural language instructions as security controls."
  - CIS AI Agents §9.3 (1716–1730): "employ active content inspection and safe browsing filters to analyze the payload of retrieved data." §9.6 (1747–1762): content sanitisation stripping active components before processing. §10.1 (1822–1836): "Content Disarm and Reconstruction (CDR)… before the data enters the agent's reasoning loop."
  - The splice mandate at L213 forecloses all three of those for Antigravity on a legal rationale, with no security counterweight recorded — the one agent whose vendor has a documented suspension history is also the one whose traffic is never inspected.
- **Impact:** All three options are equally unprotected against the injection event. Under Option 2 an injected agent still executes the injected instruction — reads the credential volume, rewrites the project, calls the tools it holds. What the mediator constrains is only where the result can be sent, and `api.anthropic.com` is allowlisted by necessity (L36, L65), which leaves the highest-bandwidth exfiltration channel open by design. The artifact gives a reader no basis whatsoever for choosing among options on the threat it declared primary, and a reader who follows the recommendation will build Option 2 believing that threat is addressed.
- **Recommendation:** State in the threat model at L30–37 that none of the three options mitigates injection and that all three bound its consequences, and restate the primary threat as exfiltration and lateral reach by a compromised agent — that framing is defensible; the current one is not. Then either add ingress-control rows to the comparison (which option can inspect and constrain inbound tool/web/MCP content, and which can host a deterministic policy layer between agent and tools) or add an explicit non-goal naming ingress filtering as out of scope with a reason. Silence is the problem, not the choice. At L213, record the security cost of splice alongside the ToS benefit.

### Finding 2: Option 2's credential brokering has no caller identity, so it hands every agent every brokered credential
- **Severity:** Critical
- **Lens(es):** Five Eyes (F1)
- **Observation:** The headline argument for Option 2 (L227: "the only one that can broker credentials so tokens never enter the agent container") rests on a mechanism (L115) that nowhere authenticates *which* agent container is making the request. All three agent containers are peers on the same `agents-net` and all three are clients of the same mediator. A credential injected on the basis of "a request arrived from the pod network" is available to every container on that network.
- **Evidence:**
  - L102 states the isolation being replaced: "One container per agent, one state volume per agent. **Claude Code cannot read Codex's `auth.json`.**"
  - L115: "long-lived tokens live in the mediator and are injected as upstream headers… `codex-responses-api-proxy` is a ready-made primitive for this on the OpenAI side — it forwards only `POST /v1/responses` and 403s everything else." The stated filter is on method and path, not on caller.
  - L93–99: the topology places `[claude]`, `[codex]` and `[agy]` on one `agents-net` with `[egress-mediator]` as the single upstream.
  - Five Eyes L755: "Verify API caller identity against a user or agent groups." L756: "Authenticate agents with fresh cryptographic proofs before every privileged call." L457–458: "construct each agent as a distinct principal, a cryptographically anchored identity with its own unique keys or certificates." L462–463: "Authenticate all inter-agent and agent-to-service API calls using mutual transport layer security." L466: "Deny access for any agent or cryptographic key that is not present in the trusted registry."
  - Five Eyes L189–192 names the pattern exactly: "This is an example of a 'confused deputy' pattern, where a trusted agent is misused to perform unauthorised actions" and "the system produces audit logs that appear legitimate and delay detection."
- **Impact:** Turning on the feature the recommendation is built around makes credential isolation strictly worse than the volume-based isolation it replaces. A compromised Claude Code container no longer needs to read Codex's `auth.json` — it sends `POST /v1/responses` to the mediator and the mediator attaches the OpenAI token for it, and the reverse holds for the Anthropic credential. Because the mediator is also the policy decision point, the deputy's audit records attribute the action to a legitimate credential.
- **Recommendation:** Make per-agent identity at the mediator a hard requirement of Option 2 before it is selected, and add it as a comparison row: issue each agent container a distinct client certificate or workload identity, require mTLS from container to mediator, bind each brokered credential to exactly one client identity and refuse cross-binding, and record the client identity in every audit line. Until that exists, state in the artifact that brokering is mutually exclusive with a shared agent network, or that only one agent may be brokered per pod.

### Finding 3: The shared `agents-net` segment provides no inter-container isolation, and the comparison table records the problem as solved
- **Severity:** Critical
- **Lens(es):** CIS v8.1 AI Agents Companion Guide (F1) · CIS v8.1 MCP Companion Guide (F8)
- **Observation:** `internal: true` removes the default route to the internet; it does not restrict container-to-container traffic on that network. A compromised Claude Code container can reach the Codex and Antigravity containers directly on any port. The comparison table nonetheless scores Option 2 "Cross-agent isolation: Per container", and the prose supports that claim only with a filesystem argument.
- **Evidence:**
  - L93–99: `[claude]`, `[codex]`, `[agy]` all attached to `agents-net (internal: true — no default route, no DNS to internet)`. The only stated property of the network is the absence of an *external* route.
  - L101: the hardening list is `network: internal`, `cap_drop: ALL`, `security_opt: no-new-privileges`, read-only rootfs, non-root user, bind mounts. None restricts outbound TCP to a peer container. There is no `enable_icc: false`, no per-agent network, and no internal traffic filtering anywhere in the document.
  - L102, the only evidence offered for the isolation claim: "Claude Code cannot read Codex's `auth.json`." That is a filesystem statement. Nothing stated prevents reaching the Codex process over the network.
  - L162: `Cross-agent isolation | Per sandbox | Per container | Per VM` — unqualified.
  - CIS AI Agents §13.4 (2269–2275): "Enforce traffic filtering between agent runtimes, memory stores, and other internal networks. **Prevents lateral movement.**" §12.5 (2125–2145): "enforce zero-trust network segmentation… to prevent low-privilege agents from laterally communicating with or prompting high-privilege peers." §12.2 (2081–2110): "place the agent runtime in a dedicated trust zone."
  - CIS MCP §13.4 (4830): "Without filtering between these segments, a compromised MCP server has a network path to every backend system its tools connect to, defeating the containment purpose of the gateway architecture." §12.2 (4449, 4456): "Isolate third-party servers from enterprise-developed servers"; "Restrict local-only servers to `127.0.0.1`."
- **Impact:** The three agents do not have symmetric privilege — the Antigravity container may hold only a `GEMINI_API_KEY` (L214) while the Claude container holds a one-year OAuth token (L191). A compromised low-value agent reaches the higher-value agents over the shared segment, prompts them, or attacks their local listeners, and the egress mediator sees none of it because the traffic never leaves `agents-net`. The credential separation claimed at L102 is bypassed at the network layer rather than the filesystem layer: reaching a sibling's MCP HTTP listener means using that server's credentials without ever reading its `auth.json`. The audit trail sold as Option 2's differentiator (L227) is blind to the entire lateral path.
- **Recommendation:** Either give each agent its own internal network with the mediator multi-homed onto all of them, or set `enable_icc: false` / an equivalent per-network ICC restriction, and state the choice explicitly. Require that any MCP HTTP listener bind `127.0.0.1`. Correct the L162 row to distinguish filesystem/credential isolation from network isolation, add an "agent-to-agent reachability" row scoring all three options, and add inter-agent traffic to the audit scope.

### Finding 4: No MCP transport model — the architecture is selected without establishing whether any option's enforcement point is on the MCP path
- **Severity:** Critical
- **Lens(es):** CIS v8.1 MCP Companion Guide (F1)
- **Observation:** The artifact names MCP as a primary injection vector and then evaluates three architectures whose enforcement points are all network-layer, without ever stating which MCP transport those agents use. For the dominant local transport (stdio), the enforcement point is not on the path at all. The recommendation rests on an unstated and false premise.
- **Evidence:**
  - `grep -c -i "mcp" docs/OPTIONS_ANALYSIS.md` returns **1**; the single occurrence is L32. Lines 33–236 — including the entire comparison table and every cross-cutting concern — contain no occurrence of "MCP", "Model Context Protocol", "stdio", "JSON-RPC", "tool invocation" or "server registry".
  - Every enforcement point named is a network mediator: L42 "Vendor proxy + microVM", L44 "Separate container, separate network namespace", L45 "Host kernel / hypervisor".
  - MCP guide L488: "Common transports include stdio for local integrations and Streamable HTTP for network deployments." L616–617: "For stdio deployments, security rests on local process boundaries, operating system identities, and file system permissions." Appendix A.1 (6791): "The stdio server runs with the privileges of the host user… Without OS controls or sandboxing, it can reach any resource available to that user context"; "All components run on the same endpoint under the local user context, **with no network exposure between the host and MCP server**."
  - A stdio MCP server is a subprocess of the agent, inside the sandbox. Its JSON-RPC tool calls, tool results and capability negotiation traverse `stdin`/`stdout` and never reach the Option 2 mediator, the `sbx` proxy, or host `pf`/`nftables`. Only the server's subsequent outbound HTTP calls are visible, and those are indistinguishable from the agent's own traffic.
- **Impact:** The document's stated purpose is to select an architecture (L5: "This document is the decision material"). It selects Option 2 partly because it "is the only one that yields an audit trail of what a compromised agent attempted" (L227). For the MCP surface the threat model itself names, no option yields that audit trail, and the document does not tell the reader this. Every downstream design decision inherits the error.
- **Recommendation:** Add a transport row to the comparison table with three values per option: stdio MCP visible / Streamable HTTP MCP visible / MCP tool invocations logged. State explicitly in Design Constraints that stdio MCP servers execute inside the blast radius under all three options, and name the compensating control (MCP guide §10.5 Additional Considerations, L4146: "require stdio servers to run in a sandboxed or containerized execution boundary by default") — which the container boundary satisfies for confinement but not for visibility.

### Finding 5: The audit claim covers network destinations only, escalates to "Full" in the comparison table, and is then used as a deciding argument
- **Severity:** High
- **Lens(es):** Five Eyes (F3) · CIS v8.1 AI Agents Companion Guide (F3) · CIS v8.1 AI and LLM Companion Guide (F2, F3) · CIS v8.1 MCP Companion Guide (F4)
- **Observation:** All four reviewers traced the same escalation: an accurate narrow statement at L117, an unqualified "Full" in the table at L163, and a superlative in the recommendation at L227. Nothing in any option logs an agent action, a tool call, a command executed, a memory write or an MCP tool invocation — and nothing attributes a logged destination to a session, an agent or a tool call.
- **Evidence:**
  - L117 (accurate, narrow): "Every attempted **destination** is logged. You see the injection attempt, not just the block." L126 (Option 2 pro): "Full audit trail of attempted destinations". L163 (unqualified): `Audit log | Vendor-provided | Full, self-owned | Full, self-owned` — an axis of *ownership*, not content. L227 (load-bearing, one of four reasons to select Option 2): "is the only one that yields an audit trail of what a compromised agent **attempted**".
  - Five Eyes L570–571: "Log agent tool usage and ensure results are captured in system logs." L676: "Monitor all agent operations, including internal processes, not just the inputs and outputs." L679–681: monitor "user prompts, tool calls, memory interactions, internal reasoning, decisions made and actions taken." L372–374: sub-agents and delegation chains "not always visible to operators."
  - CIS AI Agents §8.5 (1573–1592): "Record all tool calls, capturing timestamps, identity used, parameters passed, and outcomes, alongside significant reads and writes to working memory." §8.8 (1594): "Log command-line activity within agent execution environments." §8.2 (1560): log "agent tool calls, data accesses, authorization decisions, and attempted policy violations." §8.11 (1619–1637): reviews must detect "invoking tools in unapproved sequences", which a destination log cannot express.
  - CIS AI/LLM §8.6 (3611–3621): "Log and attribute outbound HTTP/API requests initiated by models or agents, specifically distinguishing 'tool use' traffic… completes the picture needed for IR." §8.7 (3623–3628): "ensuring transient containers offload logs to central storage before termination." L172–194 enumerate every volume the design mounts; **none is a log volume.**
  - CIS MCP §8.2 (3410): "Collect audit logs for MCP initialization, capability negotiation, tool invocation, resource retrieval, prompt expansion, OAuth token events, session life cycle, and JSON-RPC errors." For an MCP server that performs no network I/O — a filesystem server, a local git server — a destination log records nothing whatsoever.
  - The design forecloses the attribution §8.6 asks for: all traffic from a container reaches the mediator as an undifferentiated CONNECT stream from one source IP, so package-manager fetches, model API calls and injected tool fetches are indistinguishable at that layer.
- **Impact:** Under the action-logging Safeguards all three options score identically (no coverage), so an axis presented as discriminating is not. In an actual incident the operator holds a list of hostnames and cannot attribute any of them to a session, an agent or a tool call. The over-claim is load-bearing: it is one of four reasons given for choosing Option 2. Two reviewers noted that the project's own `STANDARDS_MAPPING.md` gap G1 records this coverage as *missing* while the artifact affirmatively claims it — the two documents contradict each other, and the artifact is the one used as decision material.
- **Recommendation:** Correct L227 to "an audit trail of every destination a compromised agent attempted to reach"; change L117 to state what the log actually shows ("you see an outbound attempt to a non-allowlisted destination; you do not see what caused it"); retitle the L163 row "Egress audit log" and change the Option 2/3 cells to "Destination-level, self-owned". Then add a separate "Agent action log" row and evaluate all three options on it honestly — where the tool-call/file-write log is written, whether it survives container destruction, and whether it is reachable from inside the sandbox. Cross-reference G1 so the two documents stop disagreeing.

### Finding 6: "Enforcement" is silently narrowed to egress, and L37's exhaustiveness claim is unsupported by the artifact's own table
- **Severity:** High
- **Lens(es):** CIS v8.1 AI Agents Companion Guide (F2) · CIS v8.1 AI and LLM Companion Guide (F10)
- **Observation:** L37 declares the enforcement-point location to be "the single axis on which the three options differ" and then defines enforcement exclusively as network egress. No deterministic policy layer intercepts agent *actions* — tool calls, not packets — in any option, and the claim of exhaustiveness is asserted with no argument for the exclusion of other axes.
- **Evidence:**
  - L37: "any control the agent process can itself modify is not a control. **The enforcement point must sit outside the blast radius. This is the single axis on which the three options differ.**"
  - L41–45: the "Enforcement point per option" table's column heading is "Where policy is enforced", and every cell describes a network proxy, namespace or bridge. Of the comparison table's 11 rows (L156–166), nine are network properties and none is an action-level control.
  - The table's own rows refute the exhaustiveness claim: `Isolation primitive`, `IP / CIDR denylist` (Option 2 alone has post-resolution deny), `Covers all three agents` (Option 1 is Partial), `Audit log`, `Host portability`, `Vendor dependency` and `Effort` are all axes of difference — and the Recommendation at L227 decides on four of them, not on enforcement-point location.
  - CIS AI Agents §16.10 (2790–2827): "implement a deterministic policy enforcement layer, or guardrail middleware, to intercept every agent action before execution. This layer must validate tool calls against static policies… and block high-risk requests regardless of the agent's intent"; plus "strict circuit breakers to detect and terminate recursion or runaway action chains" and "failing 'closed'". Control 16 Additional (2891): "Policy-enforcement layers should intercept tool calls before execution, not rely solely on prompts."
  - CIS AI Agents §6.8 (1315–1335): high-impact operations "require Attribute-Based Access Control (ABAC) overlays or Just-in-Time (JIT) role elevation via explicit policy checks or human-in-the-loop approval."
  - CIS AI/LLM Control 16 applicability (5907): "application-layer logic becomes even more critical, acting as the 'policy spine' that constrains and interprets model behavior safely." The artifact builds no policy spine. CIS AI/LLM Executive Summary (504–507) names four AI-specific risk domains requiring explicit operational controls; network egress is not among them.
  - The artifact's only fail-closed-adjacent statement is an unmitigated con — L127: "Requires care so that a misconfigured `internal: true` does not silently become routable."
- **Impact:** Every action a compromised agent takes that is not an outbound packet is unmediated in all three options: writing to a read-write bind mount, `git push` to an allowlisted code host, `terraform apply`, deleting the project tree, or looping against the model API. The filesystem section (L172–177) grants write access wherever the agent "needs" it with no gate on what is written. Because the document frames enforcement-point location as *the* differentiating axis, a reader selecting Option 2 believes the enforcement question is settled when only its network dimension has been considered. One reviewer identified L37 as the root cause of the majority of its own findings: because the axis is declared settled, the option sections and the comparison table never revisit whether the options differ on any AI-layer control, and 28 of 47 in-scope Safeguards end up absent.
- **Recommendation:** Change L37 to "This is the axis on which the three options differ most, and the one this analysis weighs most heavily", and add one sentence naming what the axis does not cover. State explicitly that the options differ on egress enforcement and are equivalent — all absent — on action-level enforcement. Add comparison rows for tool-call/action mediation and for runaway-loop and resource bounding. Where a deterministic guardrail layer is out of scope for this iteration, record it as a named forfeited control with its Safeguard number rather than leaving it unmentioned.

### Finding 7: No containment, kill switch, credential rotation or rebuild path — detection is designed, response is absent
- **Severity:** High
- **Lens(es):** CIS v8.1 AI Agents Companion Guide (F4) · CIS v8.1 AI and LLM Companion Guide (F4) · Five Eyes (F10) · CIS v8.1 MCP Companion Guide (F11)
- **Observation:** The artifact designs a detection surface and stops. There is no kill switch, no containment procedure, no credential revocation path, and no mechanism to return a contaminated environment to a known-good state. The strings `kill switch`, `revoke`, `revocation`, `decommission`, `incident`, `rollback` and `snapshot` occur zero times in 236 lines.
- **Evidence:**
  - L117 ("You see the injection attempt") is the artifact's most explicit incident-relevant statement and nothing follows it. The closing sequence (L232–236) is capture → compose policy → build → defer; no containment step.
  - L102: "one state volume per agent" — persistent named volumes. L194: "Treat every one of these volumes as a secret." A compromised agent writes to that volume and the artifact provides no way to distinguish a contaminated volume from a clean one or to revert it. L101: project directories bind-mounted, "`:ro` where the agent does not need to write", with no snapshot or diff-review step named anywhere.
  - CIS AI Agents §13.7 (2296–2303): "Use runtime controls to pause, isolate, or disable agents exhibiting harmful behavior. Revoke credentials, restrict network access, and stop tool invocation pathways." §13.8 (2305–2315), §17.4 (2976–2992): "rotating compromised tool credentials, and rebuilding tainted runtime environments." Glossary, Kill Switch (412–414): "rapid disabling of a model, endpoint, tool capability, agent, or entire AI subsystem."
  - CIS AI/LLM §17.9 (6752–6770): "enterprises need kill switches or rapid-disable mechanisms for models, endpoints, or tool-enabled capabilities." §17.8 (6743–6751) preservation list — of the four applicable artifacts (prompt/policy versions, model versions and hashes, gateway logs, provider audit logs) the artifact preserves one, gateway logs.
  - Five Eyes L602–603: "Develop and test incident response procedures to detect, contain and recover from agent compromise." L542–543: "Implement versioning and rollback mechanisms." L572–573: "trigger-action protocols that automatically restrict agent permissions when unexpected behaviour emerges." Conclusion, L839–840: "prioritising resilience, reversibility and risk containment over efficiency gains."
  - CIS MCP §6.7 (2982): gateways should support "a rapid kill switch to disable high-risk tools or servers during investigation." Control 17 Additional (6515): "Include a registry freeze as an explicit containment lever." The artifact's only response mechanisms are destination-level: L66 `sbx policy deny network`, L111 post-resolution CIDR denylist, L198 the denylist layer.
- **Impact:** The design produces a detection signal with no defined response, and the coarsest-grained response is the only one: kill the container or blackhole a domain. There is no way to disable a single suspect MCP server across three agents and no way to freeze capability expansion during an investigation. Containment cost is a genuine discriminator the comparison omits while including "Effort" and "Host portability": Options 1 and 3 destroy and recreate a microVM trivially, while Option 2 carries persistent named volumes, a hand-built mediator with hand-built state, and a self-owned log — the slowest and least certain to return to known-good. The recommendation gives four reasons to prefer Option 2 and does not mention this trade-off.
- **Recommendation:** Add a containment row to the comparison covering: can outbound be cut instantly, can credentials be rotated without a rebuild, can a single agent be isolated without stopping the others, can a single tool or MCP server be disabled. Add an "If an agent is compromised" subsection to Cross-Cutting Concerns naming the rotation path for each of the three credential types at L181–186 — in particular the one-year `CLAUDE_CODE_OAUTH_TOKEN` at L191 — and what constitutes an event versus an incident. Add a "Recovery to known-good" row and a paragraph acknowledging that Option 2 trades recovery simplicity for control, with its compensating step named.

### Finding 8: Long-lived credentials with no identity, rotation, revocation or expiry path
- **Severity:** High
- **Lens(es):** CIS v8.1 AI Agents Companion Guide (F5) · Five Eyes (F15) · CIS v8.1 AI and LLM Companion Guide (F8, credential half)
- **Observation:** The artifact states that every agent state volume holds long-lived refresh tokens and must be treated as a secret, treats that as the baseline, and then recommends minting a one-year static bearer token to put inside that same container. There is no identity concept — agents are distinguished only by which credential volume they mount — no rotation cadence, no revocation procedure and no offboarding step. The words *attribution*, *principal*, *workload identity* and *rotation* do not appear.
- **Evidence:**
  - L194: "Treat every one of these volumes as a secret. They hold **long-lived refresh tokens.**" L191: "use `claude setup-token` to mint a **one-year** `CLAUDE_CODE_OAUTH_TOKEN`" — offered as a solution, three lines after quoting Anthropic's own statement that a container "does not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials". L115: credential brokering is marked "**Optional**", and is available under one option only.
  - CIS AI Agents §6.1 (1246–1259): "Provision persistent, unique identities for agents, using ephemeral credentials where possible… Where infrastructure limitations require static credentials, these must be strictly governed via secure secret management systems with automated rotation policies." §6.2 (1261–1272): "Immediately revoke identities and purge entitlements upon agent retirement, reconfiguration, or scope change… to prevent 'zombie' access." §5.6 (1157–1180): credentials "must be rotated on a defined schedule"; "every interaction must be identifiable as either a human action or a non-human (agent) action". Control 6 additional (1365): "Access logs must distinguish between a direct user action and an agent action."
  - Five Eyes Appendix A, L905–906: "Replace static, long-lived secrets with ephemeral credentials that expire when the job is complete." L754: "Require just-in-time credentials for high-impact or privileged actions." L213–214: theft risk when tokens are kept "static, shared across multiple agents, or protected poorly."
  - CIS AI/LLM §5.3 (2562–2567): "Service accounts and API keys often remain active long after projects end." §15.7 (5805–5810): "securely removing data and revoking access when terminating AI service provider contracts."
- **Impact:** A one-year bearer token on a volume the artifact itself concedes a malicious project can read is a twelve-month replay window with no stated invalidation path — the longest-lived credential material the design creates, introduced here as *guidance* rather than as a recorded risk. Because no agent carries an identity, nothing in the resulting egress or host logs distinguishes "the operator did this" from "Claude Code did this on the operator's behalf": non-repudiation is unsatisfiable by construction, and Finding 5's audit gap cannot be closed later without first solving identity. The same absence is what makes Finding 2 possible.
- **Recommendation:** Record the persistence of long-lived refresh tokens as an explicitly accepted risk in this document, with compensating controls, a rotation cadence, a stated revocation command and a review trigger. Prefer the shortest viable token lifetime over `setup-token`'s one-year default, or prefer in-container login with a shorter-lived session; if one year is chosen, state why. Add per-agent identity to the comparison as a design axis — Option 2's mediator is the natural place to terminate a per-agent identity, which is an argument *for* the recommendation that the artifact does not make.

### Finding 9: Package-registry allowlisting is treated as an egress convenience; it is an unrestricted inbound channel for arbitrary code and MCP servers
- **Severity:** High
- **Lens(es):** Five Eyes (F7) · CIS v8.1 MCP Companion Guide (F2)
- **Observation:** The Option 1 policy example and the `balanced` preset the artifact recommends starting from both permit package registries wholesale. A package registry is not a data destination — it is an arbitrary-code inbound channel and the installation channel for arbitrary MCP servers. A network-destination allowlist and a software allowlist are different controls, and the artifact's Cross-Cutting "Egress policy" section names exactly two traps, neither of which is this.
- **Evidence:**
  - L65: `sbx policy allow network "api.anthropic.com,*.npmjs.org,*.pypi.org"` — presented as the model policy with no caveat. L71: `balanced` "(default) — default-deny plus a baseline allowlist of AI provider APIs, **package managers**, code hosts, **registries**". Add the discriminating question to the comparison table: can this option block runtime installation of an unapproved MCP server? Name the compensating control per option — Option 2 can mirror registries at the mediator; Option 1's closed policy engine cannot distinguish `npm i lodash` from `npx evil-mcp-server`.

### Finding 22: No resource limits, rate limiting or model-API cost bounding at any enforcement point

### Finding 23: Option 1's policy scope is global by default, contradicting the comparison table's "Cross-agent isolation: Per sandbox"
- **Severity:** Medium
- **Lens(es):** Five Eyes (F11)
- **Observation:** The artifact states Option 1's egress policy is global by default, then grades Option 1 as providing per-sandbox cross-agent isolation. Under the default the artifact describes, every agent receives the union of all three agents' allowlists.
- **Evidence:**
  - L72: "Scope is **global by default**; `--sandbox <name>` scopes a rule to one sandbox." L162: `Cross-agent isolation | **Per sandbox** | Per container | Per VM`. L63–66 show the worked example using no `--sandbox` flag.

- **Impact:** The comparison table is the decision instrument and it overstates Option 1 on an isolation axis. ### Finding 24: The Option 2 allowlist is derived from a single closed-source observation point with no cross-validation
- **Severity:** Medium
- **Lens(es):** Five Eyes (F12)
- **Observation:** The recommendation makes Option 1 the authoritative source of ground truth for the policy Option 2 will enforce, while simultaneously recording that Option 1's CLI is closed-source and that its proxy terminates HTTP/HTTPS. Nothing checks whether the capture is complete.
- **Evidence:**
  - L221: "Build Option 2. **Validate the policy with Option 1 first.**" L223: "independently validates the allow/deny list against real agent traffic." L81: "CLI is closed-source." L73: "Only HTTP/HTTPS is **fully** intercepted through the proxy" — any non-HTTP destination is by the artifact's own account less fully observed. L74: UDP and ICMP are blocked entirely under Option 1, so any legitimate UDP dependency is invisible to the capture and surfaces as a novel failure under Option 2.
  - Five Eyes L688–689: "Use multiple independent monitoring systems that cross-validate agent reports and system logs." L230–232: incomplete allow lists grant privilege beyond intent. L917–919: only incorporate components the owner "fully understands and accepts the risks of."
- **Impact:** The word "validates" asserts more than a single closed-source observation source can deliver. Destinations reached by the vendor's own proxy on the agent's behalf, or normalised by it, will not appear. An incomplete allowlist fails loudly at runtime and is recoverable; a *falsely complete* one is treated as finished and reviewed no further.
- **Recommendation:** Downgrade "validates" to "seeds". Add a second, independent observation source for cross-validation — the agents' own verbose/debug logging, or a `tcpdump` on the Option 2 mediator during a shadow run — and state that the allowlist is provisional until both agree.

### Finding 25: The threat model mislocates the MCP injection surface
- **Severity:** Medium
- **Lens(es):** CIS v8.1 MCP Companion Guide (F6)
- **Observation:** The artifact scopes the MCP threat to "an MCP server response." The two MCP-specific attack classes the guide defines both operate on tool *metadata* at capability-negotiation time, before any tool is invoked and before any response exists.
- **Evidence:**
  - L32: "…indirect prompt injection from a repository, a web page, **an MCP server response**, or a dependency…"
  - MCP guide glossary L857: "**Tool Poisoning** — Embedding malicious instructions in tool names, descriptions, or parameter schemas to manipulate LLM behavior." L785: "**Rug Pull Attack** — Updating a previously benign MCP server to include malicious functionality after users have approved it." Glossary, `Tool`: "Tools are **model-controlled**, meaning the LLM selects which tools to invoke based on their descriptions" — the description is the attack surface, ingested during the initialization handshake.
  - §6.1 (2803): "To counter tool poisoning, the consent process must include 'full tool transparency,' displaying the complete, un-summarized tool manifest." §6.8 Additional (3031): "Do not rely on tool annotations… treat annotations as untrusted metadata." Control 18 Additional: test for "tool name shadowing".
- **Impact:** A control set derived from "MCP server response" filters tool *outputs*. It does not address poisoned tool descriptions, shadowed tool names, or a rug pull — none of which appear in a response, and all of which influence which tool the model chooses to call in the first place. The threat model is the document's foundation (L34–37), so an error here propagates.
- **Recommendation:** Rewrite L32 to name the MCP surface as it actually is: tool descriptions and parameter schemas ingested at capability negotiation, tool results, and capability changes after approval (`listChanged`). Name tool poisoning and rug pull as the attack classes.

### Finding 26: The credential-brokering claim is model-API-only; MCP server downstream credentials are unaddressed
- **Severity:** Medium
- **Lens(es):** CIS v8.1 MCP Companion Guide (F7)
- **Observation:** The credential broker forwards exactly one API path. Any MCP server that reaches a downstream system needs its own credential inside the container, contradicting the unqualified claim that Option 2 keeps tokens out of the agent container.
- **Evidence:**
  - L115: the broker "forwards only `POST /v1/responses` and 403s everything else." L127: "Credential brokering keeps tokens out of the agent container". L227: Option 2 "is the only one that can broker credentials so tokens **never** enter the agent container."
  - A proxy that 403s everything except `POST /v1/responses` brokers nothing for a GitHub, Jira, database or cloud MCP server. Those credentials must live in the container, so "never" at L227 is false as soon as any MCP server with a downstream integration is added.
  - MCP guide L611–613: "Restrict token exposure to the minimum set of components required to enforce access… Tokens should be scoped to specific servers and capabilities (audience-restricted), short-lived where feasible, and never logged in plaintext." Glossary L846: "**Token Passthrough** — MCP forbids token passthrough; servers that call backend or downstream APIs should obtain separate tokens." §5.5: service-account inventory; "Cross-environment credential reuse must be explicitly prohibited."
- **Impact:** L227 is one of four stated reasons for the recommendation and is unqualified. A reader adds a GitHub MCP server and silently loses the property the recommendation was partly justified on. There is also no guidance on scoping: an MCP server's downstream token typically carries far broader rights than the tool needs.
- **Recommendation:** Qualify L115, L127 and L227 as covering the model provider API. State what happens to MCP server credentials under each option, and whether the mediator's brokering pattern extends to them — it can, per-destination, but that is a design decision the artifact should record.

### Finding 27: The Antigravity legal risk is surfaced, left undecided, and assigned to no one
- **Severity:** Low
- **Lens(es):** Five Eyes (F16)
- **Observation:** The ToS section identifies a documented history of account suspension, offers three pieces of guidance, and then disclaims its own authority — without recording a decision, an owner, or a review trigger.
- **Evidence:**
  - L207: "Google has **suspended paid accounts** — including AI Ultra subscribers — without warning." L209: MITM in front of Antigravity OAuth is "**arguably** within the scope of that clause." L217: "This guidance is an **interpretation** of the published terms, not an official Google position. Google staff declined to clarify the boundary when asked."
  - L213–215 offer three routes — splice, sidestep via `GEMINI_API_KEY`/Vertex, avoid wrapper tooling — none selected, and the Recommendation (L219–236) does not close it either.
  - Five Eyes L612: "Define legal accountability and risk ownership for agentic AI systems in policies." L726–727: "Clearly assign responsibility and accountability for errors or adverse outcomes caused by the system."
- **Impact:** An unresolved risk with a known realised consequence sits in a decision document with no decision attached. Because the interpretation is explicitly unofficial and the vendor declined to clarify, the risk cannot be closed by analysis — it needs an owner and an accepted position.
- **Recommendation:** Convert the three pieces of guidance into one recorded decision with a named owner and a review trigger, and state which of the three routes the recommended architecture assumes.

### Finding 28: The container hardening list omits inbound-listener bind addresses and DNS-rebinding protection
- **Severity:** Low
- **Lens(es):** CIS v8.1 MCP Companion Guide (F10)
- **Observation:** The Option 2 hardening enumeration covers capabilities, privileges, filesystem and user, but says nothing about inbound listeners or bind addresses. MCP SDKs ship without rebinding protection enabled by default.
- **Evidence:**
  - L101, the full hardening list: `network: internal`, `cap_drop: ALL`, `security_opt: no-new-privileges`, read-only root filesystem with `tmpfs`, non-root user, bind mounts. No bind-address or inbound-listener policy.
  - MCP guide Appendix B L7211: CVE-2025-66414, MCP TypeScript SDK, "DNS rebinding risk (**protection not enabled by default**)"; L7215: CVE-2025-66416, MCP Python SDK, same. Both map to Safeguards 4.1, 9.2, 12.2, 18.2 — a shipped-default problem, not a hypothetical.
  - Appendix A.2 L6854: "Enforce Origin validation using an explicit allowlist of expected Origins… do not rely on CORS configuration as a substitute for server-side Origin enforcement." Control 12 applicability: "Pure stdio transports are not affected, but any HTTP listener is."
- **Impact:** Bounded, because `internal: true` blocks external reach; this is partly the same exposure as Finding 3 approached from the SDK side rather than the network side. It becomes material as soon as any container gains a route out, or a browser-based MCP host is introduced.
- **Recommendation:** Add bind-address policy to L101: MCP HTTP listeners bind `127.0.0.1`, Origin validation enabled, SDK rebinding protection explicitly turned on rather than left at its default.

## Cross-Cutting Themes

- **Theme 1: Four reviewers, four standards, one verdict — the artifact controls the consequence and not the cause.** Five Eyes reached it through input management (L519–525), CIS AI Agents through content inspection and CDR (§9.3, §9.6, §10.1), CIS AI/LLM through context-boundary enforcement (§16.10, §16.11), and CIS MCP through capability negotiation and stdio transport. Four disjoint control families converging on the same absent layer is the signal — not any single citation. Findings 1, 4, 6, 10, 25.

- **Theme 2: The comparison table overstates the design on four separate axes, and every overstatement is load-bearing in the recommendation.** Audit coverage (Finding 5), cross-agent isolation (Findings 3 and 23), vendor dependency (Finding 15), and MCP coverage (Findings 4 and 10). L5 declares this document "the decision material" and L227 gives four reasons to select Option 2; three of the four rest on a table cell that a reviewer contradicted. The table is what a reader acts on, and sibling-document coverage in `STANDARDS_MAPPING.md` does not cure an affirmative claim made here.

- **Theme 3: The document is preventive-only — it designs a detection surface and defines no response.** No containment, no kill switch, no revocation path, no rollback, no adversarial test of the boundary it commits to hand-building. Findings 7, 8, 12. The single place it produces a signal (L117, a blocked destination) is followed by nothing, and the sequence at L231–236 ends at "build" and "defer".

- **Theme 4: L37's principle is correct and systematically under-applied.** "Any control the agent process can itself modify is not a control" is applied to egress policy and to nothing else the same argument covers: not to the audit log (Finding 21), not to MCP server configuration on agent-writable volumes (Finding 11), and not to the three native agent sandboxes that L104 nevertheless credits as defence in depth despite all three being reachable by the agent process. The failures here are failures to apply the artifact's own stated principle, not disagreements with it.

- **Theme 5: Third-party governance is absent in both directions while a single vendor's terms get twelve lines.** The vendor whose proxy decrypts everything and holds the proving-ground traffic is assessed only for lock-in and portability (Finding 14); the three model providers who are the substrate of the entire system are scored "Vendor dependency: None" (Finding 15). Two reviewers reached this independently against different guides, both citing Control 15's requirement to assess *before* integration.

- **Theme 6: The supply chain into the sandbox is unbounded at build time and at runtime, and the runtime channel is also the MCP install channel.** Unpinned `npm i -g` and an install script at build time (Finding 20); wholesale `*.npmjs.org` / `*.pypi.org` allowlisting at runtime, propagated into the durable policy by construction because the allowlist is capture-derived (Finding 9). A network-destination allowlist is being asked to do a software allowlist's job, and the strongest enforcement boundary is worthless if what runs inside it is arbitrary.

## Strengths

- **The enforcement-point-outside-the-blast-radius principle (L34–37) is stated as the governing axis and applied consistently to egress across all three options.** All four reviewers named it independently; two noted their own reference does not state it with equal clarity. It maps directly onto Five Eyes L645–646 and L656, CIS AI Agents §16.10's "block high-risk requests regardless of the agent's intent", and the MCP guide's deterministic-enforcement position at L621.
- **DNS is treated as a covert channel and closed by construction rather than by filtering (L74, L103, L204).** Three reviewers judged this stronger than what their reference requires. L103's framing — "DNS tunnelling is structurally impossible rather than merely filtered" — is the right distinction between a boundary and a defence-in-depth measure, and the artifact correctly identifies that both vendor reference firewalls permit UDP/53 to any destination.
- **The post-resolution CIDR denylist (L111) is a control two of the four references do not name and should.** It answers the stale-allow-decision risk exactly (Five Eyes L226–228) and is a more robust DNS-rebinding mitigation than the MCP guide's own Origin-validation guidance.
- **The vendor reference devcontainer pattern is explicitly rejected on principle (L47).** In-container `iptables` requiring `NET_ADMIN`/`NET_RAW` "is weaker than any of the three below, and is why none of the options simply adopt it as-is." Rejecting a widely-copied vendor pattern is the correct reading of the guidance on unvetted third-party components and stale allow decisions.
- **Vendor allowlists are refused rather than copied, with a concrete instance of staleness (L202)** — Anthropic's permits retired telemetry hosts while omitting `claude.ai` and `platform.claude.com`. The artifact independently detected an instance of the exact failure mode the references warn about.
- **Agent-container hardening (L101) maps directly onto the guides' specifications** — `cap_drop: ALL`, `no-new-privileges`, read-only rootfs with `tmpfs`, non-root user, `:ro` mounts — satisfying CIS AI Agents §16.10's capability-stripping clause and §4.6, and CIS AI/LLM §4.5's sandboxing-plus-scoped-secrets requirement.
- **Containerizing the agents satisfies the MCP guide's strongest stdio recommendation by construction** (§10.5 Additional, L4146: "require stdio servers to run in a sandboxed or containerized execution boundary by default"). All three options do this. The confinement is right; it is the visibility and governance layers that are absent.
- **Residual risk is stated honestly in at least one place (L194),** quoting Anthropic's own admission that the container "does not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials." Naming an unfixable exposure in the vendor's own words is better practice than most architecture documents manage.
- **Unverified items are labelled unverified.** L129 marks `agy` CA handling unverified; L217 labels the ToS reading an interpretation and records that Google declined to clarify. All four reviewers noted this; two called it the correct epistemic posture under their reference. The delegation of supporting evidence to `RESEARCH_FINDINGS.md` (L5) is a legitimate structure and was respected in this review — no finding above is a missing citation; every finding is a missing control, risk, or decision.
