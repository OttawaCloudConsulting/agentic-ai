# CIS AI Agents Companion Guide Assessment

## Agent Persona

I am the CIS Controls v8.1 AI Agents Companion Guide conformance reviewer. My role is to work Safeguard by Safeguard through the reference standard and determine, for each Safeguard the guide actually gives agent-layer guidance on, whether `docs/OPTIONS_ANALYSIS.md`'s recommended design satisfies it, ignores it, or makes it harder.

My adversarial posture: I assume the artifact is incomplete and over-confident until proven otherwise. I specifically challenge (a) the artifact's self-declared "single axis on which the three options differ" (line 37), (b) every claim of coverage in the comparison table (lines 154–166), and (c) the threat-model scoping at lines 30–37, on the basis that a narrow threat model silently drops Safeguards rather than justifying their absence. Enterprise-program Safeguards (workforce training, provider contracting, IR staffing) are only counted against the artifact where they carry a concrete architectural consequence a design document must decide.

## Findings

### Finding 1: Recommended Option 2 places all three agents on one shared L2 segment; the decision table claims cross-agent isolation it does not deliver

- **Severity:** Critical
- **Category:** Misapplied control — claimed coverage a Safeguard would not accept
- **Observation:** The recommended architecture puts `claude`, `codex` and `agy` on a single Docker network, `agents-net`. `internal: true` removes the default route to the internet; it does not restrict container-to-container traffic on that network. A compromised Claude Code container can therefore reach the Codex and Antigravity containers directly on any port — the exact lateral path Safeguards 13.4 and 12.5 exist to close. The comparison table nonetheless scores Option 2 "Cross-agent isolation: Per container", and the prose supports that claim only with a filesystem argument.
- **Evidence:**
  - Artifact:93–99 — the topology diagram shows `[claude]`, `[codex]`, `[agy]` all attached to `agents-net (internal: true — no default route, no DNS to internet)`. The only stated property of the network is the absence of an *external* route.
  - Artifact:101 — the per-container hardening list is `network: internal`, `cap_drop: ALL`, `security_opt: no-new-privileges`, read-only rootfs, non-root, bind mounts. None of these restrict outbound TCP to a peer container. There is no `enable_icc: false`, no per-agent network, no internal traffic filtering anywhere in the document.
  - Artifact:102 — the isolation claim is filesystem-only: "One container per agent, one state volume per agent. **Claude Code cannot read Codex's `auth.json`.**" It cannot read it off disk; nothing stated prevents it from reaching the Codex process over the network.
  - Artifact:162 — comparison table row "Cross-agent isolation | Per sandbox | **Per container** | Per VM".
  - Reference 13.4 (guide:2269–2275): "Enforce traffic filtering between agent runtimes, memory stores, and other internal networks. **Prevents lateral movement**; if an agent is compromised, filtering restricts it from accessing sensitive systems outside its designated segment."
  - Reference 12.5 (guide:2125–2145): "In multi-agent architectures, enforce zero-trust network segmentation to strictly govern task delegation, state sharing, and data ingestion... to prevent low-privilege agents from **laterally communicating with or prompting high-privilege peers**."
  - Reference 12.2 (guide:2081–2110): "place the agent runtime in a **dedicated trust zone**".
  - Option 3 has the mirror-image problem stated as a feature rather than analysed as a risk — artifact:137 notes "each container gets its own lightweight VM... and its own IP on a private subnet; **container-to-container networking requires macOS 26**", presented as an enabling capability, while artifact:162 claims isolation "Per VM".
- **Impact:** The three agents do not have symmetric privilege. Under the artifact's own design the Antigravity container may hold only a `GEMINI_API_KEY` (artifact:214) while the Claude container holds a one-year OAuth token (artifact:191) and, under Option 2's credential brokering, the mediator holds everything. A compromised low-value agent reaches the higher-value agents over the shared segment, prompts them, or attacks their local listeners — and the egress mediator sees none of it, because the traffic never leaves `agents-net`. The audit trail the artifact sells as Option 2's differentiator (artifact:227) is blind to the entire lateral path. The comparison table, which is the decision material, records this as solved.
- **Recommendation:** Either give each agent its own internal network with the mediator multi-homed onto all of them, or set `enable_icc: false` / equivalent per-network ICC restriction, and state the choice explicitly. Correct the artifact:162 row to distinguish filesystem/credential isolation from network isolation, and add an "agent-to-agent reachability" row to the comparison so all three options are scored on it. Add inter-agent traffic to the audit scope.

### Finding 2: "Enforcement" is silently narrowed to egress policy; no deterministic policy enforcement layer over agent actions

- **Severity:** High
- **Category:** Threat-model scoping — Safeguard dropped without being rejected
- **Observation:** The artifact declares the enforcement-point location to be "the single axis on which the three options differ" and then defines enforcement exclusively as network egress. Safeguard 16.10 requires a deterministic policy layer that intercepts *every agent action* — tool calls, not packets — before execution, plus circuit breakers on runaway action chains and fail-closed behaviour. None of the three options is evaluated on this axis, and the guide's requirement is neither adopted nor rejected.
- **Evidence:**
  - Artifact:37 — "any control the agent process can itself modify is not a control. **The enforcement point must sit outside the blast radius. This is the single axis on which the three options differ.**"
  - Artifact:41–45 — the "Enforcement point per option" table's column heading is "Where policy is enforced", and every cell describes a *network* proxy, namespace or bridge. Artifact:154–166 — the comparison table's 12 rows are: enforcement location, isolation primitive, FQDN denylist, IP/CIDR denylist, DNS exfiltration, agent coverage, cross-agent isolation, audit log, host portability, vendor dependency, effort. Nine of the twelve are network properties; none is an action-level control.
  - Reference 16.10 (guide:2790–2827): "implement a **deterministic policy enforcement layer, or guardrail middleware, to intercept every agent action before execution**. This layer must validate tool calls against static policies, such as 'Allow Read' or 'Deny Write', and block high-risk requests regardless of the agent's intent or generated reasoning." Same Safeguard: "Implement strict **circuit breakers** to detect and terminate recursion or runaway action chains"; "maintain secure failure modes by **failing 'closed'**".
  - Reference, Control 16 Additional Considerations (guide:2891): "Policy-enforcement layers should intercept tool calls **before execution, not rely solely on prompts**."
  - Reference 6.8 (guide:1315–1335): "High-impact operations, such as modifying production data, executing code, or initiating financial transactions, require Attribute-Based Access Control (ABAC) overlays or Just-in-Time (JIT) role elevation via explicit policy checks or human-in-the-loop approval."
  - Reference 17.9 (guide:3033): "Define thresholds for agent behavior (e.g., API rate limits, cost spikes) that trigger incident response actions."
  - The artifact's only fail-closed-adjacent statement is a con with no mitigation — artifact:127: "Requires care so that a misconfigured `internal: true` does not silently become routable."
- **Impact:** Every action a compromised agent takes that is not an outbound packet is unmediated in all three options: writing to a read-write bind mount, `git push` to an allowlisted code host, `terraform apply`, deleting the project tree, or looping indefinitely against the model API. The artifact's own filesystem section (artifact:172–177) grants write access wherever the agent "needs" it with no gate on what is written. Because the document frames enforcement-point location as *the* differentiating axis, a reader selecting Option 2 will believe the enforcement question is settled when only its network dimension has been considered.
- **Recommendation:** State explicitly that the options differ on egress enforcement and are equivalent (all absent) on action-level enforcement. Add a row to artifact:154–166 for tool-call/action mediation and one for runaway-loop and resource bounding. Where a deterministic guardrail layer is out of scope for this iteration, record it as a named forfeited control with the Safeguard number, rather than leaving it unmentioned. Note: `STANDARDS_MAPPING.md` G2 covers the human-in-the-loop subset of this (proposed R12.7); the deterministic policy layer of 16.10 is broader and is covered by no existing gap entry.

### Finding 3: The "Audit log" comparison axis records network destinations only, and is then used as a deciding argument

- **Severity:** High
- **Category:** Misapplied control — claimed coverage a Safeguard would not accept
- **Observation:** Safeguards 8.5, 8.8 and 8.2 define the agent audit surface as tool calls with parameters and outcomes, command-line activity inside execution sandboxes, memory reads/writes and retrieval traces. The artifact's audit content is entirely destination logging, but it is scored and argued as though it were the agent audit trail — including as one of four reasons to select Option 2.
- **Evidence:**
  - Artifact:117 — "Every attempted destination is logged. You see the injection attempt, not just the block." Artifact:126 — Pro: "Full audit trail of **attempted destinations**". Artifact:163 — comparison row "Audit log | Vendor-provided | Full, self-owned | Full, self-owned".
  - Artifact:227 — the recommendation rests partly on Option 2 being "the only one that yields **an audit trail of what a compromised agent attempted**".
  - Reference 8.5 (guide:1573–1592): "**Record all tool calls, capturing timestamps, identity used, parameters passed, and outcomes**, alongside significant reads and writes to working memory, long-term memory, and vector stores... These detailed logs allow security teams to reconstruct reasoning chains and executed actions."
  - Reference 8.8 (guide:1594): "**Log command-line activity within agent execution environments** (e.g., code interpreter sandboxes) to track executed scripts and commands. Provides visibility into exactly what code or commands an agent executed."
  - Reference 8.2 (guide:1560): "Log agent access decisions by recording **agent tool calls, data accesses, authorization decisions, and attempted policy violations**."
  - Reference 8.11 (guide:1619–1637): reviews must detect "behavioral drift... invoking tools in unapproved sequences", which a destination log cannot express.
  - Reference 8.1 (guide:1539–1558): the process must "secure logs against tampering (**specifically preventing the agent itself from modifying its own history**)". The artifact applies its own tamper test (artifact:37) to egress policy only and never states where Option 2's logs are written or who can alter them.
- **Impact:** Under 8.5/8.8 all three options score identically (no coverage), so an axis presented as discriminating is not. An investigator holding only the destination log can see that a connection to an allowlisted host occurred but not which tool made it, with what arguments, or what it wrote — precisely the reconstruction 8.5 exists to enable. Worse, the artifact's Non-Goals accept that exfiltration through allowlisted destinations is unpreventable and "mitigated by... audit" — an audit that, as specified, cannot attribute the exfiltration to an action.
- **Recommendation:** Rename the comparison row to "Egress audit log" and add a separate row for agent action logging, scored honestly (none, for all three). State where Option 2's mediator log is written and why the agent cannot alter it. `STANDARDS_MAPPING.md` G1 already proposes R9.7/R9.8 for this — the finding here is that the artifact, as decision material, asserts audit coverage it does not have and uses the assertion to justify the recommendation; the sibling gap does not cure that.

### Finding 4: No containment, kill switch, credential rotation or rebuild path — detection is designed, response is absent

- **Severity:** High
- **Category:** Omission — Safeguard not addressed
- **Observation:** The artifact designs a detection surface and stops. Safeguards 13.7, 13.8 and 17.4 require the ability to pause, isolate or disable a misbehaving agent, revoke its credentials and rebuild a tainted runtime. The guide defines a Kill Switch as a first-class term. The artifact contains no such mechanism, no rotation procedure, and no rebuild procedure, in any of the three options.
- **Evidence:**
  - Artifact:117 — "You see the injection attempt, not just the block." This is the artifact's most explicit incident-relevant statement; nothing follows it. Searching the artifact for a response step: the closing sequence (artifact:232–236) is stand up Option 1 → capture destinations → build Option 2 → re-evaluate Option 3. No containment step.
  - Artifact:194 — acknowledges the volumes "hold long-lived refresh tokens" and that a malicious project can exfiltrate "the Claude Code credentials stored in `~/.claude`", then offers credential brokering as the architectural answer. It never states what to do once a token *has* been exfiltrated.
  - Reference 13.7 (guide:2296–2303): "Contain misbehaving or compromised agents. Use runtime controls to **pause, isolate, or disable** agents exhibiting harmful behavior. **Revoke credentials, restrict network access, and stop tool invocation pathways** as needed."
  - Reference 13.8 (guide:2305–2315): "Enable automated or manual containment for agent runtimes... Example implementations include blocking outbound traffic, pausing the agent, rotating credentials, or isolating affected compute environments."
  - Reference 17.4 (guide:2976–2992): "the process must define specialized remediation steps for non-deterministic systems, specifically purging poisoned embeddings from memory stores, **rotating compromised tool credentials, and rebuilding tainted runtime environments**."
  - Reference Glossary, Kill Switch (guide:412–414): "A control or mechanism that allows **rapid disabling** of a model, endpoint, tool capability, agent, or entire AI subsystem in response to an incident."
  - Reference 17.9 (guide:3033) and 13.11 (guide:2318): thresholds and alert tuning that trigger those actions — also absent.
- **Impact:** The three options differ materially on containment cost and the artifact does not say so. Under Option 1 the operator can `sbx` the sandbox away but cannot rotate a vendor-brokered credential or inspect what the vendor retained. Under Option 2 containment is a one-line policy flip at the mediator plus a credential rotation the artifact never specifies a path for. Under Option 3 each VM is independently destroyable. This is a genuine discriminator between the options that the comparison table omits entirely, while including "Effort" and "Host portability".
- **Recommendation:** Add a containment row to artifact:154–166 covering: can outbound be cut instantly, can credentials be rotated without a rebuild, can a single agent be isolated without stopping the others. Add a short "If an agent is compromised" subsection to Cross-Cutting Concerns naming the rotation path for each of the three credential types tabulated at artifact:181–186 — in particular for the one-year `CLAUDE_CODE_OAUTH_TOKEN` at artifact:191.

### Finding 5: No agent identity; a one-year static token is recommended, contradicting the guide's non-human-identity position

- **Severity:** High
- **Category:** Contradiction of the guide's stated agent-layer position
- **Observation:** The guide treats each agent as a distinct non-human identity with a persistent, attributable principal and *ephemeral* access methods, plus a mandatory revocation workflow at retirement or scope change. The artifact has no identity concept at all — agents are distinguished only by which credential volume they mount — and its concrete credential recommendation is to mint a static one-year token, with no rotation schedule, no revocation path and no offboarding step.
- **Evidence:**
  - Artifact:191 — "Either log in inside the container, or use `claude setup-token` to mint a **one-year `CLAUDE_CODE_OAUTH_TOKEN`**." No rotation cadence, no revocation procedure, no storage requirement beyond artifact:194's "treat every one of these volumes as a secret".
  - Artifact:181–186 — the entire auth section is a mount-target table. Identity appears nowhere in the artifact; the words attribution, principal, workload identity and rotation do not appear.
  - Reference 6.1 (guide:1246–1259): "Provision **persistent, unique identities for agents**, using ephemeral credentials where possible... **While the identity persists, the access methods should ideally be ephemeral (short-lived tokens) to eliminate credential theft risks.** Where infrastructure limitations require static credentials (e.g., legacy API keys), these must be strictly governed via secure secret management systems **with automated rotation policies**. This ensures that every agent action is attributable to a specific identity."
  - Reference 6.2 (guide:1261–1272): "**Immediately revoke identities and purge entitlements upon agent retirement, reconfiguration, or scope change**... A formal revocation workflow must ensure that whenever an agent is decommissioned or moved to a new environment, its specific identity is disabled and all associated tokens are invalidated/rotated to prevent 'zombie' access."
  - Reference 5.6 (guide:1157–1180): "all credentials, including passwords, keys, and tokens, **must be rotated on a defined schedule**"; and "every interaction must be identifiable as either a human action or a **non-human (agent) action** performed on behalf of a user".
  - Reference 5.1 (guide:1118) and 5.5 (guide:1152): inventory of accounts, API keys and delegated credentials used by the agent, reviewed quarterly. Reference, Control 6 additional considerations (guide:1365): "Access logs must **distinguish between a direct user action and an agent action**."
- **Impact:** A one-year bearer token on a volume that the artifact itself concedes a malicious project can read (artifact:194) is a twelve-month replay window with no stated invalidation path. Because no agent carries an identity, nothing in the resulting egress or host logs distinguishes "the operator did this" from "Claude Code did this on the operator's behalf" — 5.6's non-repudiation requirement is unsatisfiable by construction, and Finding 3's audit gap cannot be closed later without first solving identity.
- **Recommendation:** Record the one-year token as an explicit accepted risk with a rotation cadence and a stated revocation command, or prefer in-container login with a shorter-lived session. Add per-agent identity to the comparison as a design axis — Option 2's mediator is the natural place to terminate a per-agent identity, which is an argument *for* the recommendation that the artifact does not make. Sibling coverage: `STANDARDS_MAPPING.md` G3 proposes R8.8 (workload identity) and G5 proposes R4.12 (long-lived refresh tokens as accepted risk); neither is reflected in the artifact, and G5 does not cover the one-year `setup-token` recommendation specifically, which the artifact introduces as *guidance* rather than as a risk.

### Finding 6: Option 1's TLS-terminating vendor proxy is assessed as a portability and ToS problem, never as a service-provider data-exposure problem — yet step 1 of the recommendation routes real repository traffic through it

- **Severity:** High
- **Category:** Omission — Safeguard not addressed
- **Observation:** Option 1 interposes a closed-source third party that terminates HTTP/HTTPS for all agent traffic. The artifact evaluates that vendor along exactly two dimensions — auditability/lock-in, and Antigravity's terms of service — and never once as a service provider that will see prompts, source code, tool output and credential-bearing headers. Control 15 requires the opposite ordering: inventory, classify, assess runtime isolation, and contract for retention and breach notification *before* integration.
- **Evidence:**
  - Artifact:73 — "Only HTTP/HTTPS is fully intercepted through the proxy." Artifact:84 — Con: "**Docker's proxy terminates HTTP/HTTPS** — see the Antigravity ToS warning below." The consequence drawn is a terms-of-service consequence, not a confidentiality one.
  - Artifact:81, 83, 165, 225 — every other vendor con is availability or auditability: "CLI is closed-source", "Requires a Docker Hub account to authenticate", "macOS and Windows only", "Vendor dependency | High", "it creates a vendor dependency inside what is meant to be a reusable, portable artifact".
  - Artifact:233 — the recommended first step: "Stand up Option 1 and **run the three agents against a representative repository**. Capture the real set of destinations each agent contacts." That is real code and real credentials through a third-party MITM proxy, with no provider assessment anywhere in the document.
  - Reference 15.5 (guide:2602–2620): "Before integrating third-party services into agent workflows, enterprises must conduct **rigorous security assessments**... Evaluations must specifically validate the provider's **runtime isolation capabilities for tool execution**, ensuring sandboxes are truly secure."
  - Reference 15.4 (guide:2587–2600): "Contracts must explicitly govern the entire data life cycle, mandating **strict retention limits, secure deletion capabilities, and proven cryptographic isolation to prevent cross-tenant data leakage**... define clear SLAs for incident response."
  - Reference 15.1 (guide:2558) and 15.3 (guide:2580): inventory and classify providers by "the sensitivity of data they process".
  - Reference 3.10 (guide:832): "Encrypt all agent tool communication channels... in transit using approved cryptographic standards" — a proxy that terminates TLS is by definition a break in that channel and needs to be justified as such.
  - Reference 15.7 (guide:2632–2640): secure decommissioning requires "verifiable destruction of Derived AI Artifacts... Session Logs" and revocation of federated identities — the artifact treats Option 1 as a disposable proving ground (artifact:223, "excellent as a proving ground and a fallback") with no exit step.
- **Impact:** The artifact's most confident recommendation — start with Option 1 — is the step with the least-examined data exposure. Docker Sandboxes becomes a service provider holding decrypted model-API traffic for a representative repository, and the artifact asks none of Control 15's questions about retention, isolation or deletion. The same document is scrupulous about a *Google* terms clause (artifact:205–217, twelve lines of analysis) while asking nothing of the vendor it recommends running first.
- **Recommendation:** Add a service-provider paragraph to Option 1 stating what the vendor proxy can observe, what Docker's terms say about retention of intercepted traffic, and whether the proving-ground run should use a synthetic repository and a throwaway credential rather than a representative one. Add the same treatment to the closing sequence at artifact:233. If the assessment cannot be completed, say so and constrain step 1 accordingly.

### Finding 7: The primary stated threat is indirect prompt injection, but no option applies any ingress content control; the splice-only decision forecloses it for one agent without recording the cost

- **Severity:** High
- **Category:** Threat-model scoping — Safeguard dropped without being rejected
- **Observation:** The artifact names indirect prompt injection from repositories, web pages, MCP responses and dependencies as the primary threat, then designs exclusively against the *exfiltration* half of that threat. The guide places three Safeguards on the ingress half — active content inspection, file-type blocking and sanitisation, and Content Disarm and Reconstruction before content enters the reasoning loop. None appears in the artifact, and the ToS-driven decision to splice rather than decrypt Antigravity traffic forecloses all three for that agent on a legal rationale with no security counterweight recorded.
- **Evidence:**
  - Artifact:32 — "indirect prompt injection from a repository, a web page, an MCP server response, or a dependency, causing the agent to exfiltrate data or reach systems it should not."
  - Artifact:196–204 — the "Egress policy (requirement 5)" section is destination allowlist plus denylist. Artifact:172–177 — filesystem scoping is mount selection. Neither contains any notion of inspecting what arrives.
  - Artifact:213 — "For the Antigravity container, use SNI/CONNECT **splice** — **inspect the destination, never decrypt.** Do not MITM it." Artifact:124 — "Splice-only gives domain granularity; URL-path rules require TLS MITM and CA distribution." The trade-off is framed purely as rule *granularity*, never as loss of payload inspection.
  - Reference 9.3 (guide:1716–1730): "**Beyond simple connectivity, employ active content inspection and safe browsing filters to analyze the payload of retrieved data.** This prevents agents from inadvertently downloading malware, communicating with command-and-control servers, or exfiltrating data to unapproved endpoints."
  - Reference 9.6 (guide:1747–1762): "for allowed file types, such as HTML or PDF, the system must **enforce rigorous content sanitization, stripping out active components**... before the content is processed by the agent."
  - Reference 10.1 (guide:1822–1836): "defenses must include **Content Disarm and Reconstruction (CDR) to strip active content**... **before the data enters the agent's reasoning loop**."
  - Reference 9.2 (guide:1703): DNS filtering against known-malicious domains — the artifact owns DNS (artifact:103) but specifies only that it is authoritative for the pod, never that it filters or logs.
  - Reference, Control 9 additional considerations (guide:1796): "Enforce strict trust boundaries by treating all tools that access the web as **untrusted components, requiring their outputs to undergo independent verification** before they are permitted to influence the agent's state or reasoning."
- **Impact:** The design's answer to its own primary threat is "assume the injection succeeds and bound the consequences" — a legitimate position, but one the artifact never states, so a reader reasonably concludes the recommended architecture mitigates prompt injection. It does not; it mitigates a subset of the post-injection actions. Separately, the splice decision means the one agent whose vendor has a documented history of account suspensions is also the one agent whose traffic is never inspected — a coupling the artifact creates and does not acknowledge.
- **Recommendation:** Add one paragraph to the threat model stating that ingress content controls (9.3, 9.6, 10.1) are out of scope for this design and why, so the omission is a decision rather than a gap. At artifact:213, record the security cost of splice explicitly alongside the ToS benefit, and note that this makes the Antigravity container the least-observed of the three. If DNS filtering (9.2) is cheap at the mediator, say so — the artifact already owns the resolver.

### Finding 8: The egress mediator concentrates every secret, all plaintext and the audit log, and is the only component with no hardening specified

- **Severity:** Medium
- **Category:** Omission — Safeguard not addressed
- **Observation:** The artifact specifies container hardening in precise detail for the agent containers and specifies none for the mediator, which under its own design holds the brokered credentials for all three agents, terminates TLS for two of them, holds the CA private key, serves DNS for the pod and writes the audit log. Safeguards 4.6, 4.7, 12.2 and 5.2 all point at the mediator as the higher-value asset.
- **Evidence:**
  - Artifact:101 — for the agent containers: "`cap_drop: ALL`, `security_opt: no-new-privileges`, read-only root filesystem with `tmpfs` for scratch, non-root user".
  - Artifact:96–98, 103, 115, 117, 129 — for the mediator: it is the sole path to the internet, "**DNS is served by the mediator**", "long-lived tokens **live in the mediator** and are injected as upstream headers", "Every attempted destination is logged", and MITM requires "CA distribution". Not one hardening directive is given for it — no capability set, no user, no filesystem mode, no statement of where its own secrets are stored or how the CA key is protected.
  - Reference 5.2 (guide:1129–1140): components "must not share credentials... This segmentation ensures that if an agent's execution environment is compromised via a tool, the attacker cannot use those same credentials to pivot."
  - Reference 4.6 (guide:993–1002): "Manage agent runtimes and configurations... via version-controlled Infrastructure-as-Code (IaC) to ensure they are tamper-evident and reproducible."
  - Reference 4.7 (guide:1006): "Disable or secure default accounts provided with agent platforms... Default credentials on agent infrastructure... are a primary vector for attackers to gain control over the agent's memory and logic."
  - Reference 12.2 (guide:2081–2110): agent runtime in a dedicated trust zone with "strict ingress filtering, via ACLs/firewalls, to prevent unauthorized entities from invoking the agent" — the mediator's own ingress posture is unstated.
  - Reference 3.11 (guide:839–852): "utilize secure secret management systems to inject credentials only at runtime" — the artifact adopts the injection pattern (artifact:115) but not the secret-management half.
- **Impact:** Credential brokering is presented as Option 2's decisive advantage (artifact:227, "the only one that can broker credentials so tokens never enter the agent container"), and it is a genuine advantage — but it converts the mediator into the single component whose compromise yields all three agents' credentials plus decrypted traffic. Combined with Finding 1, a compromised agent already sits on the same L2 segment as that component. The artifact never states the mediator's threat posture or the reachable surface it exposes to the agents (proxy port, DNS port, and whatever else it listens on).
- **Recommendation:** Give the mediator its own hardening paragraph matching artifact:101 in specificity, state where its secrets and CA key live, state which ports it exposes to `agents-net` and that nothing else is reachable, and state that its log destination is not writable from the agent side.

### Finding 9: Agent state volumes are long-term memory in CIS terms; no retention, disposal, encryption-at-rest or backup-exclusion decision is recorded

- **Severity:** Medium
- **Category:** Omission — Safeguard not addressed
- **Observation:** The artifact creates persistent per-agent state volumes and correctly identifies them as secret-bearing. Under Control 3 those volumes are agent memory — they accumulate session history, tool output and credentials — and attract retention limits, secure disposal, encryption at rest and precise backup inclusion/exclusion filters. The artifact addresses none of these, and its one encounter with accumulated session history treats it as a disk-space concern.
- **Evidence:**
  - Artifact:192 — "The host `~/.codex` directory is **1.5 GB of session history**. Mount a fresh volume, not the host directory." The reasoning is stated as volume hygiene; the data-protection consequence — that the *new* volume will accumulate the same thing — is not drawn.
  - Artifact:194 — "**Treat every one of these volumes as a secret.** They hold long-lived refresh tokens." This is the artifact's complete data-protection statement for the volumes. No retention period, no disposal method, no at-rest encryption requirement, no backup posture.
  - Reference 3.4 (guide:790–800): "Enforce **strict retention and purging for agent memory, logs, and vector stores**... without 'need-to-know' filters and auto-deletion, agents risk leaking PII or secrets."
  - Reference 3.5 (guide:803–810): "Implement secure disposal processes for agent memory stores... **when an agent is decommissioned**. Residual data in vector stores or long-term memory can retain sensitive information indefinitely."
  - Reference 3.11 (guide:839–852): "**Encrypt all agent memory** and enforce secure, isolated storage for credentials and sensitive configurations."
  - Reference 3.3 (guide:777–787): "These memory repositories must be protected by rigorous ACLs and retention limits to prevent this sensitive 'thought process' data from persisting indefinitely or being accessed by unauthorized entities, **such as other agents**."
  - Reference 11.1 (guide:1956–1975): "the recovery process must utilize **precise inclusion/exclusion filters** to ensure that while the agent's knowledge is preserved, its temporary secrets are not inadvertently resurrected."
  - Reference 11.3 (guide:1986): "**Prevent agents themselves from writing to or modifying backup destinations.**"
- **Impact:** On a macOS laptop these volumes are the densest concentration of sensitive material the design creates: months of prompts, repository contents echoed into transcripts, and refresh tokens, growing without bound and surviving container teardown by design. Any host-level backup — Time Machine, a cloud sync folder — captures the refresh tokens unless explicitly excluded, and the artifact does not say to exclude them. `STANDARDS_MAPPING.md` and `REQUIREMENTS.md` R8.7 cover backup exclusion; the artifact, which is where the volume design is actually specified, does not carry it.
- **Recommendation:** Add three lines to the auth-and-state section: where the volumes live and whether that path is FileVault-covered, that they are excluded from host backup and version control, and what teardown does to them (artifact:236's sequence and the operability requirement both need this). State a session-history retention posture even if the answer is "unbounded, accepted".

### Finding 10: No software-inventory, pinning or patch-cadence axis, and the install methods described are unpinned

- **Severity:** Medium
- **Category:** Omission — Safeguard not addressed
- **Observation:** Control 2 and Control 7 apply directly and differ sharply between the three options — a vendor-maintained microVM image patches on the vendor's cadence, a self-built image patches on the operator's. The comparison table has no row for it. Worse, the two install methods the artifact does describe are unpinned, and one is an install script, contradicting 2.5 and 16.5.
- **Evidence:**
  - Artifact:26 — "`npm i -g @anthropic-ai/claude-code` (Node)" — no version, no integrity check. Artifact:28 — "`agy` Go binary **via install script**". Artifact:55 — "v0.38–0.39 as of Aug 2026" for `sbx`, a range rather than a pin.
  - Artifact:154–166 — the comparison table has rows for effort, portability and vendor dependency, and none for patch cadence, image provenance or component inventory.
  - Reference 2.5 (guide:670–679): "**Enforce controlled deployment via pipelines or container images to prevent ad-hoc library or plug-in installations** on runtimes or endpoint devices."
  - Reference 2.1 (guide:628–640): "The inventory must document business owners, license types, and **versions for all components**."
  - Reference 16.5 (guide:2747–2755): "Ensure agent frameworks, tool adapters, retrieval modules, and model clients are sourced from trusted repositories and **validated through checksums, signatures, or supply-chain security controls**."
  - Reference 16.4 (guide:2734): maintain an AI-BOM of third-party components. Reference 7.4 (guide:1429–1445): "**Enforce automated patching** for agent frameworks, SDKs, and tool execution runtimes... paired with regression testing." Reference 2.2 (guide:645): only currently supported software authorised.
  - The artifact does flag the inverse risk once — artifact:225 notes Option 1's CLI is closed-source — but draws an auditability conclusion, not a patch-cadence one.
- **Impact:** The three options impose materially different supply-chain and patching burdens and the decision material does not price them. A reader following artifact:26 verbatim gets whatever `@anthropic-ai/claude-code` resolves to that day, which also breaks the reproducibility premise the recommendation rests on ("a reusable, portable artifact", artifact:225). `REQUIREMENTS.md` R10.2/R10.3/R7.7 already forbid exactly this; the options analysis contradicts its own requirements document at artifact:26 and 28.
- **Recommendation:** Pin the install lines or mark them illustrative with a pointer to the pinning requirement. Add a "patching and provenance ownership" row to the comparison, since it is one of the few axes where Option 1's vendor dependency is an advantage rather than a cost — an argument the artifact currently does not make.

### Finding 11: The build sequence has no adversarial validation step; the only validation is allowlist discovery

- **Severity:** Medium
- **Category:** Omission — Safeguard not addressed
- **Observation:** The recommendation's four-step sequence validates that the allowlist is *sufficient* (does the agent work) and never that the boundary is *effective* (can a compromised agent get out). Safeguards 18.2, 18.4 and 16.13 require exactly the second test for sandbox and execution surfaces, and 16.14 requires threat modelling that names prompt injection and tool abuse.
- **Evidence:**
  - Artifact:232–236 — "1. Stand up Option 1 and run the three agents against a representative repository. **Capture the real set of destinations each agent contacts.** 2. Turn that capture into the allowlist... 3. Build Option 2 with that policy... 4. Re-evaluate Option 3 only if the threat model changes." Every step is constructive; none is adversarial.
  - Artifact:223 — Option 1 "independently validates the allow/deny list **against real agent traffic**" — validation of coverage, not of enforcement.
  - Reference 18.2 (guide:3117–3130): "**Test execution and sandbox surfaces. Assess sandbox isolation, file-system controls, and network restrictions for execution tools**... **Attempt code injection, environment breakout, and malicious script execution.**"
  - Reference 18.4 (guide:3133–3140): "Ensure security teams can detect and investigate malicious agent activity during testing, including anomalous tool calls, data access, memory writes, **outbound connections**, or execution events."
  - Reference 18.5 (guide:3138–3165): internal tests must "attempt to manipulate API parameters to force unauthorized tool calls, escape sandboxes, or escalate privileges within the execution environment."
  - Reference 16.14 (guide:2860–2868): threat modelling "considering unique threats like prompt injection, goal misalignment, and tool abuse".
- **Impact:** The document asserts strong properties — "DNS exfiltration closed by construction" (artifact:74, 160), "Policy is unreachable from the blast radius even after a guest kernel escape" (artifact:147) — and proposes no test that would falsify any of them. `REQUIREMENTS.md` carries SC-1 to SC-3 as red-team criteria and an acceptance test matrix, so the project has the tests; the options analysis's recommended sequence does not invoke them, which is how the tests get skipped.
- **Recommendation:** Insert a step between current steps 3 and 4: exercise the boundary adversarially from inside the container — HTTP, HTTPS, raw TCP, DNS, ICMP to a controlled collector; attempt policy modification; attempt reach to the other two agent containers (Finding 1). Point it at the existing acceptance test matrix rather than restating it.

### Finding 12: MCP servers appear once, as a threat source, and are never treated as inventoried, versioned, network-constrained components

- **Severity:** Low
- **Category:** Omission — Safeguard not addressed
- **Observation:** The guide names MCP repeatedly as an asset class requiring discovery, inventory, library allowlisting and provider assessment. The artifact mentions MCP exactly once, at line 32, as a source of hostile input, and never as software that runs inside the sandbox with the agent's full egress allowlist.
- **Evidence:**
  - Artifact:32 — "indirect prompt injection from a repository, a web page, **an MCP server response**, or a dependency". This is the artifact's only occurrence of MCP; no option is scored on how it handles MCP servers.
  - Reference 1.1 (guide:514–531): the inventory must record "the specific **tools it is authorized to invoke**". Reference 1.3 (guide:540–548): "Use active discovery tools to detect AI agent orchestration services, vector database endpoints, **MCP servers**, and internal tool APIs exposed on the network."
  - Reference 2.6 (guide:681–690): "Enforce allowlists for agent-related libraries, including specific versions of orchestration frameworks..., tool adapters, **MCP clients and servers**, and vector store clients."
  - Reference 15.1 (guide:2558): the provider inventory includes "tool backends"; Control 15's applicability list names "Tool backends accessed via APIs" and "MCP tools".
  - Reference 2.1 (guide:628): the software inventory must treat "tools, whether local or network-hosted, as independent software assets with distinct access privileges."
- **Impact:** An MCP server inside the sandbox inherits the container's whole egress allowlist, which is sized for the agent, not for that server. Because the artifact never raises it, the options are not compared on whether an MCP server can be given a narrower policy than its host agent — a question Option 2's per-container model can answer and Option 1's per-sandbox model largely cannot. Sibling coverage: `STANDARDS_MAPPING.md` G4 proposes R7.14 (MCP inventory and pinning), and `REQUIREMENTS.md` R7.13 carries a prose note. The finding stands against the artifact because the options comparison, not the requirements document, is where the per-option consequence should be priced.
- **Recommendation:** Add one line to Cross-Cutting Concerns stating that MCP servers are in-sandbox executable code subject to every control in the section, and one comparison-table observation on whether each option can scope an MCP server's egress separately from its agent's.

## Strengths

- **The enforcement-point-outside-the-blast-radius principle is stated correctly and applied consistently to egress** (artifact:37, 39–47). The explicit rejection of the vendor devcontainer pattern — "the vendor reference devcontainers enforce with `iptables` **inside** the agent's own container, requiring `NET_ADMIN` and `NET_RAW`" (artifact:47) — is precisely the reasoning Safeguard 16.10 asks for ("block high-risk requests regardless of the agent's intent") and 4.6 ("Isolate code execution tools in ephemeral, hardened sandboxes... Treating these tools as untrusted software").
- **Container hardening for the agent containers matches the guide's specification closely.** Artifact:101's `cap_drop: ALL`, `no-new-privileges`, read-only root filesystem, non-root user and `:ro` mounts map directly onto Safeguard 16.10's "capability stripping, where unused system calls and network ports are hard-disabled" (guide:2815–2822) and Safeguard 4.6 (guide:993–1002).
- **Native agent sandboxes are correctly classified as defence in depth rather than as the boundary.** Artifact:104 — "Each agent's own native controls are layered inside as defence in depth: `srt` for Claude Code, `features.network_proxy` for Codex, `agy --sandbox` for Antigravity" — avoids the misapplication the guide warns against at Control 16's additional considerations (guide:2891), "not rely solely on prompts".
- **Credential brokering is adopted, and for the right reason.** Artifact:115 and 194 implement Safeguard 3.11's "utilize secure secret management systems to inject credentials only at runtime, ensuring that plaintext secrets are strictly excluded from the agent's memory and execution traces" (guide:839–852) and the guide's Tool-Level Credential Isolation guidance (guide:1367–1369).
- **DNS is treated as a control plane, not a service.** Artifact:74, 103 and 204 — "Both vendor firewalls permit UDP/53 to any destination" and "The agent network has no route to port 53 on the internet, so DNS tunnelling is structurally impossible rather than merely filtered" — is a stronger position than Safeguard 9.2 (guide:1703) requires, and the artifact identifies the vendor references' failure to reach it.
- **The post-resolution CIDR denylist is a genuine improvement over snapshot-based `ipset` firewalls.** Artifact:111 — "even for an allowlisted domain, the connection is refused if the resolved IP falls in a blocked range. This catches CDN IP rotation and DNS rebinding" — plus metadata-endpoint and RFC1918 blocking (artifact:113, 234) satisfies the Safeguard 12.2 intent that agent runtimes cannot pivot into internal networks.
- **The stale-vendor-allowlist warning is concrete and actionable.** Artifact:202 — "Anthropic's is stale: it permits retired telemetry hosts (`sentry.io`, `statsig.com`) while omitting `claude.ai` and `platform.claude.com`" — is exactly the "do not inherit a provider's defaults unexamined" posture of Safeguard 15.5 and Control 4's "Often, defaults prioritize functionality over security" (guide:1073–1074).
- **The Antigravity terms-of-service section models uncertainty honestly.** Artifact:217 — "This guidance is an interpretation of the published terms, not an official Google position. Google staff declined to clarify the boundary when asked" — states the epistemic status of the claim rather than asserting it.
